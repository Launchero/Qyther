# Qyther — DOX root rail

DOX is installed here. AGENTS.md files are binding work contracts for their subtree. This file is the rail: repo-wide rules, global preferences, and the Child DOX Index. Closer docs control local work details; no child doc may weaken DOX.

## Core Contract

**Read before editing**

1. Read this file.
2. List every file or folder you expect to touch.
3. Walk from the repository root to each target path and read every AGENTS.md on that route, following the Child DOX Index.
4. Nearest doc = local contract; parents = repo-wide rules. On conflict the closer doc wins local detail — never DOX itself.
5. Do not rely on memory. Re-read the applicable chain in the current session.

**Update after editing** — every meaningful change requires a DOX pass before the task is done. Update the nearest owning doc when the change affects purpose, scope, ownership, durable structure, contracts, workflows, required inputs/outputs/permissions/artifacts, quality standards, behaviour or communication preferences, or any AGENTS.md create/delete/move/rename. Update parents when parent-level structure, ownership or a child index changes; update children when a parent change alters local rules. Delete stale or contradictory text immediately. Small edits that change no contract may leave docs unchanged, but the pass still happens.

**Closeout** — re-check changed paths against the chain → update nearest owning docs and affected parents/children → refresh every affected Child DOX Index → remove stale text → run existing verification where runnable **and** drive the changed behaviour in the live app (## Live Verification) → report docs intentionally left unchanged and why.

**Child doc shape** — create a child AGENTS.md when a folder becomes a durable boundary with its own purpose, rules, responsibilities, workflow, materials or quality standards. Section order: Purpose, Ownership, Local Contracts, Work Guidance, Verification, Child DOX Index. Leave Work Guidance empty if no standards exist yet; leave Verification empty if no check exists yet.

**Style** — concise, current, operational. Document stable contracts, not diary entries. Broad rules in parents, concrete detail in children. Direct bullets with explicit names. Do not duplicate a rule across scopes unless each scope needs its own version. Delete stale notes instead of explaining history.

## Repo-Wide Invariants

- **Every IPC channel is four hand-synced sites.** Channel string in `src/preload/preload.ts` → `ipcMain.handle` in `src/main/ipc/*` → call site in renderer → type in `src/renderer/types/electron.d.ts`. There is no shared schema and no codegen. Contract detail lives in `src/main/ipc/AGENTS.md`. **Shared boundary value types are the one exception and the direction of travel:** `src/shared/ipc/` holds types-only modules (plus pure Electron-free parsers) that main, preload and renderer all import, so a payload shape cannot be declared three ways. A channel whose payload has a shared type still needs the four sites — the shared module removes the duplicate *definition*, not the registration.
- **There are three shared IPC validator modules.** `validateUrl` and `validatePath` exist only as local functions inside `src/main/ipc/handlers.test.ts:6,48,82` — most production handlers validate inline, and that test file tests its own copies. The three that live in their own Electron-free, production-imported module are `isCommandSafe` (`src/main/ipc/command-guard.ts`, called by the `command:execute` handler, covered by `command-guard.test.ts`) and `checkBaseUrl` (`src/main/ipc/api-config-guard.ts`, called by `api-config.ts` before `api-config:save` persists a renderer-supplied `baseUrl` and before `api-config:test` fetches it with a key attached — that channel used to fetch any URL the renderer named, which is the same preload-bypass class as `command:execute`) and `isSafeSearchQuery`/`isUsablePath` (`file-guard.ts`, called by the `file:search`, `file:open` and `file:revealInFolder` handlers, with `file-guard.test.ts` asserting main’s pattern list still equals preload’s). Tests that import production code: `command-guard.test.ts`, `mcp/client-contract.test.ts`, `chat-cancel-turn.test.ts`, `api-config-guard.test.ts`, `file-guard.test.ts`, `windowManager.test.ts`, `logger.test.ts`. Validation is still uneven elsewhere: `url:open` checks in main, `file:search` and `file:open`/`file:revealInFolder` check in both layers (`file-guard.ts` holds main’s copy, and `file-guard.test.ts` fails if it drifts from the preload list), while `file:everything:status` has nothing to validate. Because the preload layer is renderer-reachable, a direct `ipcRenderer.invoke` bypasses those guards — which is also why any DevTools `Runtime.evaluate` against the debug port is OS command execution until main checks. Full per-channel table in `src/main/ipc/AGENTS.md`.
- **Renderer never imports from main.** It talks through `window.electronAPI`; the type comes from `src/renderer/types/electron.d.ts`, which re-exports `typeof electronAPI`. `src/renderer/types.d.ts` is a stale hand-maintained duplicate that still WINS for the channels it declares — do not extend it **unless the channel is already declared there**, in which case you must, because that file wins and `typecheck` fails otherwise (five sites, not four). `src/preload/types.d.ts` is no longer a duplicate: it is a three-line re-export of the renderer type and must stay empty. Shared boundary types come from `src/shared/ipc/` via `import type`, which is erased at build and breaks neither rule.
- **Sandbox is on**: `app.enableSandbox()` (`main.ts:40`) with `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true` (`windows.ts:87-89`). Preload compiles to CJS and is loaded as `../preload/preload.cjs`. Dev-only relaxations: remote-debugging port 9222 (`main.ts:53`).
- **No `requestSingleInstanceLock` and no blur-to-hide exist in this codebase.** `close` is `preventDefault`ed **unconditionally** and turned into a hide; its only escape is the `isQuitting` flag set by `app.on('before-quit')`, which lets the app's own Quit paths (tray Quit and `app:quit`) destroy the window (`windows.ts:15-18,129-137`), and `window:hide` (`handlers.ts:50`) hides directly (`windows.ts:163-171`). Do not document either of those two absent mechanisms as current behaviour.

## Process & Resource Lifecycle

**Every process, session, native handle, timer and subscription this app acquires must have exactly one named disposer, registered where it is acquired.** This is a build-time contract, not a code-review preference — read it before adding any of the six classes below.

- **Child processes are bounded, always.** Every `exec` / `execFile` / `spawn` in `src/main/**` must pass a `timeout`. Node's `exec` defaults to `timeout: 0`, which means *no timeout*: a command that never exits holds its shell and its IPC call open forever, with nothing to kill it. `maxBuffer` is the companion — the 1 MB default turns a merely chatty command into a truncation error. The seven current child-process sites are: `ipc/handlers.ts` (`command:execute` via `promisify(exec)`, 30 s / 10 MB), `utils/esRunner.ts` `searchFiles` (10 s / 10 MB), `utils/esRunner.ts` `isEverythingRunning` (3 s / 1 MB), `services/pi/toolbox.ts` (`execute_command`, 30 s default / 10 MB), `services/desktop/screenshot-capture.ts` (a `powershell.exe` `spawn` with `timeout: 5000`), `main.ts` (`execSync` Playwright install, 120 s, `stdio: 'ignore'` so no `maxBuffer`), and `services/pi/toolbox.ts` again for the `explorer.exe` `spawn` — the one **documented exception**: `detached` with `child.unref()` and no `timeout`, because Explorer exits on its own and the tool's 1.5 s wait is pacing, not a bound. Anything new that can wedge gets a bound in the same change; a new `exec` with neither is a defect on arrival.
- **Acquisition cannot orphan.** `MCPService` construction connects every configured server, so `mcp/client.ts` builds each connection into a **local**, publishes the batch onto the field only after `listTools()` resolves, and `close()`s the locals on failure (`publish`/`closeConnections` in that file). Assigning first meant a throw left a half-built adapter parked for the next `initialize()` to overwrite — and `initializeWithRetry` makes three attempts, so three orphaned stdio children. **Any new handle whose constructor opens something follows this shape.**
- **Quit is a real, bounded, ordered teardown.** `app.on('will-quit')` cannot await, so `main.ts` calls `event.preventDefault()`, runs `buildShutdownSteps()` through `lifecycle.ts`, then `app.exit(0)`. `lifecycle.ts` (`createShutdown`) owns four properties: steps run in **array order, sequentially**; each is bounded by `SHUTDOWN_STEP_DEADLINE_MS` (2 s) so one wedged disposer cannot strand the rest; `run()` never rejects; and `run()` is **memoised**, which is what makes the unconditional veto safe. The current order — `global-shortcuts` → `tray` → `browser-agent` → `mcp` → `pi-desktop-agent` → `ipc-handlers` → `database` — is a contract: the koffi message-pump interval is first because it is what holds the event loop open, IPC handlers are removed near the end to prevent new requests during final teardown, and the database is last so its `close()` flush captures anything written during teardown. **`browser:cleanup` deliberately does not kill the shared Playwright child** — that child belongs to `mcpService` and is released by the `mcp` step; killing it there would break chat. **SIGTERM and SIGINT are handled** (`main.ts:38-55`): without handlers, Node.js exits immediately without cleanup when Docker/Kubernetes/systemd send SIGTERM or the user presses Ctrl+C (SIGINT). The handlers route into `app.quit()` so the normal Electron shutdown path fires `will-quit` and runs the ordered teardown. A `signalReceived` flag prevents re-entrant shutdown if multiple signals arrive.
- **Native and database handles are released, not abandoned.** `DatabaseManager.close()` existed with **zero** production callers and is now the `database` step. `PiDesktopAgent.dispose()` (tesseract worker + UIA facade) and `WindowsDesktopAdapter.cleanup()` were already wired. `LangChainAgent.cleanupBrowserAgent()` nulled its session id without clearing `browserSessionTimeout`, so a live 5-minute timer outlived the work it watched — it clears it now, and it is the browser subtree's release path too (one owner, one call, now the `browser-agent` step). `BrowserMemoryStore` went the other way: it was deleted outright when its only writer — a graph node — disappeared, rather than kept alive by a shutdown step nothing else used.
- **Renderer resources: every timer, frame and subscription has a teardown, and every `await` before `setState` has a mounted guard.** A `setTimeout`/`requestAnimationFrame` whose id is discarded fires after unmount; an effect that awaits `window.electronAPI.*` and then `setState` writes into a dead tree. The guard idiom is fixed and named: **`isMountedRef`** (declared, set `true` in a mount effect, flipped `false` in its cleanup) — `hooks/useFileSearch.ts` is the reference implementation. Timers live in a `useRef` beside the state they clear, are re-cleared on re-arm so rapid transitions do not stack, and are cleared in an unmount cleanup. `on*` subscriptions keep returning their unsubscribe. An IPC call that cannot be cancelled — and none of them can — is made **not to be started** after teardown rather than pretended cancellable (`sleepWhileMounted`).
- **Pollers carry an in-flight guard.** A `setInterval` whose async tick can outrun its own interval produces overlapping requests and out-of-order dispatch into a reducer. One outstanding request maximum; a tick arriving while one is in flight skips rather than queues.

**Verification, by class.** The lifecycle module is unit-gated: `src/main/lifecycle.test.ts` imports the production `createShutdown` and pins order, continue-past-a-failure, continue-past-a-timeout, never-reject, no-leaked-timer, and memoised re-entry. Renderer teardown is gated by `npm run lint` plus `npx vitest run src/renderer/` (12 files / 63 tests, 2026-10-16), but the honest limit is that **no test mounts the app shell** — the two component mounts are the Ask surface (`components/ask-mode/AskModeExpanded.test.tsx`) and the command bar, so palette, results-list and settings-dialog timer cleanup is only truly proven by driving the palette. Quit behaviour has **no automated coverage at all** — `main.ts` cannot be imported under vitest because it pulls `electron` and `koffi` at module scope. That makes hand-driving the tray Quit path mandatory, not optional.

**Closeout rule.** A change that acquires one of the six resource classes above is not done until it has registered the matching disposer **in the same change**. Creating a resource and deferring its release to a later task is how the desktop database ended up with a `close()` method that nothing called; deleting a resource whose only writer has gone is the other half of the same discipline, and is how the browser trajectory store was retired.

## Live Verification

**This app is tested by running it and driving it like a Windows user. Always.** `typecheck`, `lint` and `test` prove the code compiles and that unit logic holds — they are not evidence that a feature works. A task touching anything the user can see, feel or press is not done until the changed path has been exercised against the live app and the observed result has been reported.

- **What must be driven live:** window geometry, mode changes and the height tween; global shortcuts and the koffi hook; show/hide, the Escape ladder and focus; palette and results UI; theme and motion; any new or changed IPC channel end to end; chat/agent streaming; generated documents (open the file that was written, do not trust the tool result). If the change is in one of those areas, run it.
- **Quitting is hand-driven, and the observation is the process tree, not the log.** No harness verb may close or quit the app (`scripts/harness/AGENTS.md`), so the `will-quit` path is driven through the tray menu. Prove it by recording the child processes before and after: `Get-CimInstance Win32_Process` filtered on the app's pid tree, before and after tray Quit. The pass condition is that no `node`/`npx` MCP child and no renderer/GPU child survives the main pid, and that the app actually exits. A `Released <name> in <n>ms` log line is evidence the step ran; it is **not** evidence the process died, and neither is `Shutdown complete`.
- **Sequence, every time.** Start `npm run dev` yourself in the background — the harness deliberately never launches, quits or navigates the app. Then `npm run harness:preflight` and honour its refusal (a second instance, a pid/endpoint mismatch, scale drift or a foreign foreground window are all valid stops; do not work around them by killing someone else's process or dialog). Then drive and observe.
- **Drive through `scripts/harness/`, not through the page.** `node scripts/harness/cli.mjs <verb> --flag value`: `who`, `state`, `list_windows`, `ax_snapshot`, `reveal`, `hide`, `click_element`, `click_role`, `click_at`, `type`, `key`, `scroll`, `drag`, `set_mode`, `clear_input`, `wait`, `screenshot`, `save_frame`. Use **flags, not the JSON blob** — Windows PowerShell 5.1 strips the double quotes out of a single-quoted argument before the native process sees it. Same verbs over MCP with `npm run harness:mcp` (`type_text`/`press_key`/`wait_for` there). Input is OS-level `SendInput` by contract: never synthesize a DOM event, never `el.click()`, never call `window.electronAPI` to put the app into the state you are testing — that tests your fake, not the app. **Trust the exit code**: every verb declares its own success predicate, so a failed verb exits non-zero rather than printing a healthy-looking result. Assert with the harness's reads (`state`, `screenshot`, `ax_snapshot`), which are DOM ground truth, not inference from the code you just wrote.
- **Prefer `click_role` to `click_element`.** The accessibility tree is live over CDP (101 nodes), so a control can be addressed by the role and accessible name a person would use — `click_role --role textbox --name "Search for files"` — which survives a restyle that renames a class, where a CSS selector is a guess at something the caller cannot see.
- **Run the standing gate** `npm run harness:selftest` (18 steps) after any change to the window, palette, hook, tween or focus paths, and report the pass count measured in this session. Running it catches behaviour, not a drifted pin: when such a change moves or renames a value the harness pins (a DOM id, an accessible name, a `window:*` event, the tween timing or mode heights), update the harness **and its doc** in the same change — the pinned-surface contract is `scripts/harness/AGENTS.md` ("the harness pins the app's observable surface"). Editing the harness itself is governed by that doc.
- **Hand-driving is for what the harness cannot reach** — the tray icon and its menu, taskbar docking, a second monitor, the Windows animation setting, an installer build. Do those by hand and say which; do not substitute "I ran `npm run test`" for either.
- **Report the drive, and never imply one that did not happen.** Closeout states the actions taken and what the app returned (heights, frames, `hidden`, row counts, timings). If the app cannot be run — no `node_modules`, another instance owns the window, machine unavailable — state that plainly, list which static checks ran instead, and leave the behaviour marked unverified.

## Global Preferences

Karpathy operating principles: think in features not lines; treat instruction files as tunable code; context quality dominates output; simplicity bias — no speculative code, no abstractions for single-use, no unrequested configurability; bounded autonomy; instruction-first development. Maximum 50 lines per function. Every changed line must trace to the user's request.

Bounded autonomy defaults: 1–3 files per agent, 300s per experiment, one unambiguous metric, `git reset` on failure.

### Subagents

Delegate for context isolation and parallelism, never to offload verification. A subagent starts with a fresh context: it has not read this file, knows nothing of the current task, and its report is a claim until re-derived here.

- **Two shapes only.** Scouting — "which files implement X", "where is Y registered", "what imports Z", "does this count still hold" — goes to the read-only search role with an explicit thoroughness level. Independent units that touch disjoint files go to the work role, one unit each, dispatched concurrently. Never delegate a single-file edit, a mechanical rename, or anything one read answers.
- **The roster is harness-provided.** Read the available subagent list before dispatching; never assume a named role exists, and never hard-code a role count (same rule as the browser-tool invariant).
- **Every prompt carries what the child cannot derive.** The applicable AGENTS.md chain as paths the child must read itself — never a summary of it, since the child must obey it — plus the exact files in scope, the invariants binding those files (four IPC sites, pristine `components/ui/`, a `logger.ts` registry row, the family row in `pi/families.ts`), read-only vs may-write, the acceptance check (`npm run typecheck` / `lint` / `test`, or the subtree's own Verification section), and the report format: file paths plus symbols and command output, not prose summaries.
- **One owner per file.** Two children never edit the same file. Cut parallel work by file, never by step — the hand-synced IPC sites and the derived `families.ts` index are where concurrent edits drift silently.
- **The parent owns the DOX pass.** A child cannot see the whole change set, so children never edit `AGENTS.md`. The Closeout rule above applies to the parent's session: re-read the chain, update nearest docs, refresh Child DOX Index rows.
- **Verify before citing.** Re-derive every path, symbol, count and green check in this session before it reaches a doc or a report. "The subagent ran the tests" is not a result — and per `docs/AGENTS.md` rule 5, counts are recounted from code, never copied from a child's or another doc's number.
- **Continue, don't re-prime.** For a follow-up inside the same unit, continue that child session by its id instead of spawning a fresh one that re-reads the same files. Background dispatch only for work the next step does not depend on.
- **Isolate colliding writes.** When parallel children must write, give each its own git worktree and merge only here.
- **Secrets and captured material stay with the parent.** `.env` is untracked — never ask a child to read or print it. Any child touching `docs/assets/` inherits the capture-harness privacy gate: no out-of-repo paths in a generated frame.
