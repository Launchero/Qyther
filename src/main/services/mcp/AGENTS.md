# src/main/services/mcp — DOX child contract

Parent: `../AGENTS.md` (agent-runtime rail).

## Purpose

The MCP **client** layer: spawns/connects to external stdio/http MCP servers, exposes their tools as Pi tools, and filters which tools reach which family (browser_ prefix → `browser` family, everything else → `mcp` family).

## Ownership

- `client.ts` (312 lines) — `MCPService` (`:116`), the `MCPServerConfig` interface (`:22`), per-server connect (`connectServer`, `:197`), publish (`publish`, `:218`), bounded failure close (`closeConnections`, `:240`), JSON-Schema→Pi conversion (`toPiTool`), the 30 s per-call budget (`MCP_TOOL_TIMEOUT_MS`, `:20`, passed as `timeoutMs` at `:103`) and the `mcpService` singleton (`:312`).
- `client-contract.test.ts` (102 lines) — drives the real `MCPService` against the repo's own stdio MCP server (`scripts/harness/mcp-server.mjs`), proving that server-native tool names pass through unchanged and that the connection is bounded and released. It imports `MCPService` from `./client` and `loadPreferences` from `../../preferences`, so it is a gate on this repo's code, not only on the library's.
- `tool-router.ts` (80 lines) — the `INTENT_TOOL_MAP` / `KEYWORD_TOOL_MAP` prefix tables. **Dead in production:** the only importer of `getMCPToolsForIntent` / `detectRelevantTools` anywhere in `src/` is `tool-router.test.ts`. The intent strings those maps key on were what the deleted `classifyNode` emitted; there is no classifier, so nothing asks for tools by intent any more. `tool-router.test.ts` stays green while proving nothing about the shipped path — see Local Contracts before touching it.
- `mcp-config.json` at repo root — the server inventory (config, not code). **Tracked and committed** (`.gitignore` names it, but an already-tracked path is not ignored), so a fresh clone already has it and never needs the example copied. It currently carries `filesystem`, `sequential-thinking` and `playwright` with no credentials in any `env` block — **and because this repository is public, that is a hard rule: a key put into an entry's `env` block is published.** `mcp-config.example.json` is documentation of the shape only, with the `filesystem` placeholder path `C:\Path\To\Your\Project`, not a real home directory). The example file declares `filesystem`, `sequential-thinking`, `notion` and `github` and **no `playwright` server** — so a fresh clone gets zero browser tools, silently.
- Read-only cross-boundary input: `prefs.mcp` from `src/main/preferences.ts` (enable/disable store, owned outside this folder).
- The IPC control surface (`src/main/ipc/mcp-handlers.ts`) is NOT owned here; its channel rules live in `src/main/ipc/AGENTS.md`.

## Local Contracts

- **Config file shape** is `MCPServerConfig` (`:22-29`): `command`, `args`, optional `disabled` (`:25`), optional `env`. A parse failure or missing `mcp-config.json` degrades to `{}` with a warn (`loadFromConfigFile`, `:250`, warn at `:252`) — "no servers" is never a crash, so check the warn line before assuming the file loaded.
- **Client-only, verified**: `McpServer` / `StdioServerTransport` have zero hits in `src/` **code**. This repo's `src/` hosts NO MCP server; never write server code here. The one server in the repository is the UI harness at `scripts/harness/mcp-server.mjs`, which is outside this subtree and outside `src/`. (The `type McpServerDef` at `client.ts:33` is this repo's own descriptor shape, not the SDK's server class — a grep for `McpServer` matches it, which is why the invariant grep below is scoped to code and annotated.) **Dependency truth**: `@earendil-works/pi-mcp` (1.2.0) is the only MCP package `src/` imports (`client.ts:1-8`). `@modelcontextprotocol/sdk` is a `devDependency` — for `scripts/harness/mcp-server.mjs` only, never for `src/`. `langsmith` and all four `@langchain/*` packages are gone.
- **Init gate**: `initialize()` (`:123`) returns early when preferences disable the whole feature (`:127-130`, `MCP disabled in preferences`) and is idempotent via `isInitializedFlag` (`:119`, checked `:124`). If the merge yields no servers — including the common fresh-clone case where the untracked `mcp-config.json` is absent — it logs `No MCP servers enabled` (`:139`) and returns with `isInitialized()` still false. The Ask loop then binds an **empty `mcp` family** and an empty **`browser` family** and still answers normally: `buildAskToolboxes` degrades to `[]` per family and `buildAskSystemPrompt` drops empty families, so the model is never advertised a capability with no tools. That is a silent-degradation path, not an error — see the runtime log line below before concluding the servers loaded.
- **Config merge precedence** (`:160-190`), in order:
  - `mcp-config.json` entries load via `loadFromConfigFile` (`:250`), whose path is built from `MCP_CONFIG_PATH` (`:54`), and `PROJECT_ROOT` (`:53`) is derived from `import.meta.url` as `join(dirname(fileURLToPath(import.meta.url)), '../..')` — **not** bare `__dirname`, which is undefined at this module's scope because `main.ts` installs its global polyfill only after this module is evaluated. The main bundle is emitted as a single `out/main/main.js`, so `../..` from the bundle resolves to the **repository root in dev** and the **app root in a packaged build**; `electron-builder` does not ship `mcp-config.json` (it is outside `build.files` and gitignored), so a packaged build falls into the missing-config branch and loads zero config-file servers.
  - A config server is dropped if `disabled: true` in the JSON (`:176`) **or** if preferences enable other servers but not it (`:177`, `prefEnabledNames` built at `:172`).
  - Preferences may additionally contribute stdio/http servers absent from the config file; http is the only non-stdio transport supported (`StdioTransport` / `StreamableHttpTransport`, `:198-201`).
- **Warm-up**: `initializeWithRetry` (`:266`, 3 attempts, linear backoff) is called from `src/main/main.ts:121` during startup; failure there is logged as a warning, not fatal — the deferred path is the IPC one below.
- **Acquisition must not be able to orphan, and this is why each connection is built in a local.** `connectServer(def)` (`:197`) constructs the transport and a `new McpClient({name:'qyther'})` locally, `await client.connect(transport)`, `await client.listTools()`, and on **any** throw calls `client.close()` before rethrowing (`:209-214`) — closing the client is the only release the transport's child needs. Nothing is written to the instance until every connection is open: `publish(opened)` (`:218`) sets `connections`, `tools`, `serverNames` and `isInitializedFlag` only after the batch succeeds, and the failure path routes through `closeConnections(opened)` (`:240`), which never rejects. The earlier shape assigned `this.client` before the list call, so a throw parked a half-built adapter with live stdio children that the next `initialize()` (gated only on the still-false flag) overwrote — and `initializeWithRetry` tries three times, so one misconfigured server could orphan three processes. `browser/stateful-browser-agent.ts` has the identical shape for its fallback client, where it was worse: `cleanup()` was gated on `usingFallback && fallbackClient`, so a throw before `usingFallback = true` left the orphan unreachable from *both* ends.
- **Cleanup path**: `cleanup()` (`:301`) closes every connection and resets state, and it is reached from `main.ts`'s shutdown list (`mcp` step) as well as the IPC toggle path. `browser:cleanup` deliberately does **not** call it — on the shared path the Playwright stdio child belongs to this service, not to the browser subtree, and killing it there would break chat. That child is released at quit, and on a config change via `mcp:toggleServer` / `mcp:toggleTool`.
- **Tool attribution**: `serverToolCounts` (`:120`) is filled in `publish()` (`:221-223`) from each connection's own tool list — per server, not by guessing a name prefix. Duplicate tool names across servers are logged and skipped (`:225-228`), which is the client-side half of the rule that makes `pi/families.ts:buildFamilyIndex`'s duplicate throw the loud one. Read the counts through `getServerToolCounts()` (`:297`).
- **Consumers**: tools reach the model via `pi/tools/browser-tools.ts` (`mcpService.getTools().filter(name.startsWith('browser_'))`) and `pi/tools/mcp-tools.ts` (the rest); this folder only exposes `getTools()` (`:281`) and `getToolsByPrefix()` (`:285`). **`getToolsByPrefix` has no production caller** — the two families filter the flat `getTools()` list themselves, so the prefix split that actually matters lives in `pi/`.
- **`tool-router.ts` is not on the shipped path.** Its two maps (`INTENT_TOOL_MAP`, `KEYWORD_TOOL_MAP`) keyed on intents a deleted classifier emitted, and the only importer is its own test. Do not add a server prefix to those maps as if it made the server reachable — what makes an MCP tool reachable is `mcpService.getTools()` plus the family prefix filter in `pi/tools/`. Deleting the router is a legitimate cleanup that needs its own request; until then, treat its test as a library-shape test, not as coverage.
- **Adding a tool needs no code at all**: it is an entry in `mcp-config.json`. Code changes are only needed when a new server's tools must be claimed by a *different family prefix*, which is a `pi/families.ts` row plus a `pi/tools/*.ts` filter change, not a router edit.
- **Stale doc**: `MCP-CONFIG.md:34-38` claims a `USE_MCP=true` env flag gates MCP — it is read nowhere in `src/`. Do not cite or honour it; the gate is `prefs.mcp.enabled`.

## Work Guidance

- Add an MCP server, full recipe: ⓪ edit `mcp-config.json` directly — it is tracked, so a clone already has it and there is no copy step ① entry in `mcp-config.json` (`command`/`args`/`env`, optional `disabled`) ② ensure it is enabled in preferences ③ restart dev and confirm the `Initialized with N tools across M servers: …` line (`client.ts:157`) and `getServerToolCounts()` (`:297`) ④ if its tools should belong to the `browser` family, they must be named `browser_*` — that prefix is the only routing this folder has.
- **There is no intent routing left to update.** `tool-router.ts`'s `INTENT_TOOL_MAP` keys were the strings the deleted `classifyNode` emitted (`research`, `general`, `browser`, `desktop`, `document`); Ask mode has no classifier, so an entry there connects nothing. Do not add one.
- Server tools missing at runtime: check the `disabled`/`prefEnabledNames` gate (`:176-177`) before suspecting the spawn.
- Do not add per-server custom connection code — stdio and http are the only transports (`:198-201`).
- Tool names follow `<serverPrefix>_<tool>` only when the **server** emits them that way; pi-mcp adds no prefix of its own, so server-native names reach `getTools()` unchanged — which is what `client-contract.test.ts` asserts and what makes the `browser_` filter meaningful. The consequence is a real one: two servers that ship the same tool name collide, and `publish()` keeps the first and warns on the duplicate (`:225-228`).
- After any config change, restart via the IPC path (`mcp-handlers.ts` re-`initialize()`s, cleaning up first); there is no file watcher.
- Temporarily disable a server with `disabled: true` in its (untracked) `mcp-config.json` entry (`client.ts:25`) rather than deleting it; the preferences enabled-set (`:172`) is a second, independent switch — a server loads only when both allow it.
- Invariant to preserve: `grep -rn "McpServer\|StdioServerTransport" src/ --include="*.ts" --include="*.tsx"` must stay free of **server** usage (client-only contract). Scope it to code — this doc and `src/main/ipc/AGENTS.md` name the strings while banning them, so an unscoped grep always matches itself, and `client.ts:33`'s own `type McpServerDef` matches the pattern without being a server.
- Per-server secrets go in the entry's `env` block (`client.ts:180` carries `cfg.env` into the server definition, `:200` hands it to `StdioTransport`) — not in the app's top-level env, so each server keeps its own override. Since the live `mcp-config.json` is untracked, secrets in it stay machine-local and out of git.
- This folder exposes no channel strings; every renderer-facing `mcp:*` channel and its validation lives in `src/main/ipc/mcp-handlers.ts` under the `ipc/AGENTS.md` four-site rule.

## Verification

- `client-contract.test.ts` drives the real `MCPService` against the repo's own stdio MCP server (`scripts/harness/mcp-server.mjs`) and proves that server-native tool names pass through unchanged — it is this subtree's one real gate. `tool-router.test.ts` covers the prefix-match logic of code **nothing in the app calls**, so treat it as a shape test and not as evidence the router works. Run with `npm run test`.
- Manual gate: `npm run typecheck`, then `npm run dev` and read the MCP log line at `client.ts:157` (`Initialized with N tools across M servers: …`). `node_modules` is installed here, so both gates run.
- The `MCP config not found at …` warn (`client.ts:252`) is now the *abnormal* path: `mcp-config.json` is tracked, so a clone has it, and the warn only fires after someone deletes or renames it — which loses every config-file server with no error and no crash. The tracked file declares `playwright`; `mcp-config.example.json` does not, so overwriting one with the other is how the browser family silently ends up with zero tools. That clone also has **no `playwright` server**, because the example file does not declare one — `browser` binds zero tools and Ask mode still answers.
- Negative check worth running manually: point one config entry at a bogus `command` and confirm `initializeWithRetry` retries 3× (`client.ts:266`, linear backoff `1000 * (i + 1)`) and startup still succeeds (`main.ts` wraps the call in a non-fatal warn), proving the failure path is not fatal — and that no stdio child survived the three attempts.
