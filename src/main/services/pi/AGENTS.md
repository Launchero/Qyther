# src/main/services/pi — DOX child contract

Parent: `../AGENTS.md` (agent-runtime rail). Local contract wins local detail; parents win repo-wide rules.

## Purpose

The Pi agent runtime that replaces the LangGraph stack. Owns the model bootstrap against Qyther's custom OpenAI-compatible endpoint and the desktop toolbox. The mandate is **Pi-native, not Pi-shaped-to-fit-LangGraph**: use Pi's own composition model (`Agent`, typed `AgentEvent`, TypeBox tools) rather than adapting Pi to Qyther's graph idioms.

Phase status: **done and wired.** `pi/` is now the *whole* Ask-mode runtime, not a node inside a graph: `../../ipc/chat-handlers.ts` calls `runAskTurn()` (`ask-turn.ts`) once per turn, and that function builds one Pi `Agent` over every tool family. There is no `AskGraph`, no intent classifier and no delegation between agents — the model routes by choosing a tool, and `families.ts` turns that choice into the label the renderer shows. The pump no longer touches the desktop agent at all: it owns one `AbortController` per turn and passes its `signal` into `runAskTurn`, which attaches the listener that calls `agent.abort()`. `abortPiDesktopRun()` and `runPiDesktopTask()` still exist and have **zero production callers** — see `agent.ts` in Ownership.

The LangGraph/LangChain packages are gone from `package.json` entirely (`langgraph`, `core`, `openai`, `mcp-adapters`). The deleted files were `../langgraph/**` (the whole folder, including its `AGENTS.md`), `../browser/browser-subgraph.ts`, `../document/document-subgraph.ts`, `../document/document-delegation.ts`, the browser and document planner/recovery/verifier-LLM/memory modules, and `langchain/agent.ts`'s ReAct half.

## The Ask loop (`ask-turn.ts`)

This is the whole of Ask mode. Everything below this heading is a contract a change can break.

- **One `Agent` per turn, built from the assembled families.** `runAskTurn` calls `buildAskToolboxes()` (memoised at *this* call site, not inside `ask-tools.ts`, so a test can inject its own set via `AskTurnDeps.toolboxes`), flattens them, builds the family index, and constructs `new Agent({ initialState: { systemPrompt, model, tools, thinkingLevel: "off" }, streamFn, sessionId, toolExecution: "sequential" })`.
- **`toolExecution: "sequential"` is load-bearing, not a preference.** The renderer folds a completion onto an open step by matching the step string, which is the tool name — two concurrent calls to the *same* tool would fold onto each other and leave a spinner that never resolves. Parallel also buys nothing: these are screen, disk and network actions a user expects to see happen in order.
- **Cancellation reuses the desktop hang fix, unchanged.** `withAbort` races `agent.prompt()` against the turn's `AbortController`; `ask-handlers` owns that controller and `chat-handlers.ts` aborts it on Stop and on timeout alike.
- **`ASK_RUN_TIMEOUT_MS` is 10 minutes** (`ask-turn.ts:47`), a whole-turn budget. `HISTORY_TURNS = 10` bounds how much transcript is replayed.
- **`AskNotConfiguredError`** is thrown before any model call when `isPiConfigured()` is false or `getPiModel()` returns undefined. The pump maps it to the renderer's not-configured envelope; it is not a crash.
- **The system prompt is built per turn from the bound families.** `buildAskSystemPrompt(sessionId, bound, query)` advertises only families whose toolbox is non-empty, and appends `buildBrowserSkillSection(query)` — on-disk `SKILL.md` material matched against this turn's query — when `browser` is bound. That replaces the deleted `skillRouter`/`loadSkills` pair; same material, read at the point it is useful.
- **The label comes from the tool, not from a classifier.** `families.ts` maps tool name → family → `AgentLabel`, and the translator emits `chat:agent-change` on the first tool of a turn. Before any tool runs the label is `IDLE_AGENT_LABEL` (`"General"`). `ui`, `web` and `mcp` all map to `"Research"` because the renderer's label set is closed and has no sixth label; `AGENT_LABEL_BY_FAMILY` is the one place to change that.
- **Step copy follows the same rule, and is a separate value.** The turn label answers *who is acting*; `displayLabelFor()` answers *what this row is called*. Each toolbox already declares a human `label` per tool (`toolbox.test.ts` asserts it for all 32 desktop tools), so `NamedTool` carries it and the index resolves it. **Do not add a name→copy map on either side of the bridge.** `ask-events.ts` used to translate five tool names onto deleted graph-node strings so three legacy badges would keep working; the other 39 first-party tools fell through to their internal `snake_case` identifiers, and the file's own comment called that "a readable label, not a blank". `families.test.ts` now reads both sources and fails if either map returns.
- **`buildFamilyIndex` throws on a duplicate tool name across families.** Pi resolves a call by name, so a duplicate silently makes one family unreachable. `browser` and `mcp` therefore filter the *same* `mcpService.getTools()` list by disjoint prefixes (`browser_` vs not), and `getMcpToolbox` excludes `browser_*` deliberately for this reason.
- **An empty family is a valid state, not a bug.** Each toolbox builder degrades to `[]` rather than throwing when its substrate is unavailable, and the prompt drops empty families so the model is never advertised a capability with no tools.

## Local Contracts

- **The endpoint is `openai-completions`, not `openai-responses`.** Pi's `openaiProvider()` returns `Provider<"openai-responses">` — the Responses API. `BASE_URL` points at a Chat-Completions-only proxy, so `provider.ts` uses `createProvider` + `openAICompletionsApi()` from `@earendil-works/pi-ai/api/openai-completions.lazy`. That is the same shape `deepseekProvider()` uses. **Do not "simplify" this to `openaiProvider()`** — it will fail at request time, not at compile time.
- **Provider id is `"qyther"`, never `"openai"`.** A distinct id keeps `models.getModel(PROVIDER_ID, id)` addressable and out of Pi's built-in OpenAI catalog.
- **Env contract is `MODEL`, `API_KEY`, `BASE_URL` only, read at the point of use** — `provider.ts` resolves them through `modelId()`, `apiKey()` and `baseUrl()`, with `MODEL` defaulting to `qwen3.6-plus`. There is no second config surface and no `login()`; the app resolves the key through its own `api-config` settings, so `auth` is ambient-only (`API_KEY_AUTH`, a bare `ApiKeyAuth` with `resolve` and no `login`). `isPiConfigured()` is `apiKey() && baseUrl()`, and it is what `langchain/agent.ts`'s `isReady()` reports through to `chat:initialize`. **Never move these back to module-scope `const`s**: the previous shape captured `undefined` because the bundled main graph evaluates this module independently of `main.ts`'s `import 'dotenv/config'`, which made Ask mode render its not-configured card on a correctly configured machine. `provider.test.ts` pins the call-site read.
- **`compat` is deliberately pessimistic.** `supportsStore`, `supportsDeveloperRole`, `supportsStrictMode` are all `false` and `maxTokensField` is `"max_tokens"` — a non-OpenAI proxy implements none of these. Loosening them sends parameters the endpoint will reject.
- **Import allowlist.** `@earendil-works/pi-agent-core`, `@earendil-works/pi-mcp`, and from `pi-ai` only the root plus `/api/openai-completions.lazy`. **Never** import `/all`, `/compat`, `builtinModels()`, or `/bedrock-provider` — `compat` is side-effectful and self-declared for deletion, and the rest drag the whole provider catalog in.
- **Construction is lazy, not at module load.** `getPiModels()` memoises on first call so importing this folder costs nothing; cold start is budgeted and `main.ts` is not modified.
- **`getPiStreamFn()` memoises, it does not merely bind.** `Agent` takes `streamFn` in its constructor, so each call must return the same reference. `provider.test.ts` asserts identity.
- **`getModel` is not narrowed by the provider's `TApi`** — `getPiModel()` must keep the `hasApi(model, "openai-completions")` check, or it widens to `Model<Api>` and the `openai-completions` options type is lost.

## Work Guidance

- **`PiTool` is a variance workaround, not a convenience alias — do not "simplify" it away.** `AgentTool.execute` is declared as a *property*, so under `strictFunctionTypes` its `params: Static<TSchema>` (= `unknown`) is checked contravariantly. That means **no** concrete `AgentTool[]` annotation accepts a tool whose `execute` destructures its schema-derived params — not `AgentTool<any>[]`, not `AgentTool[]`, not even `Agent.state.tools`. `PiTool` re-declares `execute` with **method** syntax (whose parameters are bivariant) and widens `params` to `any`, which is the only escape found. Consequences:
  - Annotating a factory with anything else, or widening `params` to a concrete schema, reintroduces the error once per tool.
  - Each tool still declares its real `parameters` schema inline, and that stays the single source of truth for its `execute` signature. **Never hand-duplicate a params type** next to the schema.
  - `TUnsafe` is **not** exported by `@earendil-works/pi-ai`; an earlier attempt using it cannot compile.
- **Three LangChain-era indirections are already gone from the toolbox, and must not come back:**
  - `inferStatusFromTool` (a tool-name string map) → every desktop tool reports `details.status`. This was edit 6 of the desktop folder's six-coupled-edits rule. **Scope it honestly: the pattern is gone from `pi/`, not from the repo** — `browser/stateful-browser-agent.ts` still keeps a private `inferStatusFromTool(toolName)` that maps `navigate`/`click`/`type|fill` onto `BrowserTaskProgress.status`, so the `browser:executeTask` progress path mirrors names while the Ask path reads the tool's own `details`. Fixing that is a browser-subtree change, not a reason to reintroduce a map here.
  - `DANGER_POLICY` (32 rows consulted by name) → `details.verifies`, set only on `close_window`, which is the sole tool that runs `GroundTruthVerifier`. Omitted rather than `false` when not applicable, so "asked and declined" is distinguishable from "never opted in". Because the flag now lives on the tool, the exhaustiveness check that used to guard the map is unnecessary — a tool cannot forget its own flag.
  - the `_type: 'screenshot_result'` marker that `desktop-agent.ts` string-matched to build a multimodal `ToolMessage` → `screenshot` returns a real `ImageContent` block.
- **Tools never throw.** That contract is inherited from `desktop-tools.ts` and is load-bearing: the model must be able to read a failure and recover. `fail()` sets `isError: true` rather than relying on a throw, and `toolbox.test.ts` asserts it. Keep the lazy `await import()` of `input-simulation` / `screenshot-capture` / `tesseract.js` / `child_process` / `fs` inside handlers — module-load FFI is what keeps this subtree survivable off-Windows and in the Vite graph.
- **The bridge is pure and switches on a discriminated union, so a new event arm is a type error, not a silent drop.** That is the whole point of replacing the LangChain path's `metadata.langgraph_node` + `RESPONSE_NODE_SET` string routing. `events.ts` takes an `AgentEvent` and a callback bag; it constructs no `Agent`, touches no Electron, and makes no network call, so the entire translation is testable from a recorded event list. `default:` is an intentional no-op for the five arms it does not surface (`agent_start`, `turn_start`, `message_start`, `message_end`, `tool_execution_update`).
- **The agent preserves exactly two behaviours the loop cannot supply for itself.** (1) The initial screenshot: skipped for simple window tasks (`isSimpleWindowTask`, carried over verbatim from `desktop-agent.ts:209-210`, a cold-start optimisation worth ~1s) and degraded to a text-only first turn when capture fails or returns no data URL. Both branches are contracts. (2) The pixel verifier, which runs only for a tool that set `details.verifies` and feeds its verdict back with **`agent.steer()`** — the native replacement for the old corrective-`HumanMessage` injection, since `steer` queues for the next model turn instead of mutating the transcript behind the loop's back.
- **The hang is FIXED, and the fix is three cooperating pieces — do not undo any one of them.** Observed 2026-10-15 with a live endpoint: a 3-step task (`launch_app` → `wait` → `close_window`) never settled, main sat at 0% CPU with the log frozen — an unresolved promise, not a busy loop. It is now closed on three sides, and removing any of them reopens it:
  1. `withAbort` (`abort.ts`) races `agent.prompt()` against the run's own `AbortController`, so the node settles the moment the pump gives up instead of waiting on work that never resolves.
  2. `run()` creates that controller per run (`agent.ts`), hands it to Pi and to every tool, and treats `controller.signal.aborted` as an expected outcome rather than a failure — it returns `{aborted: true}`, it does not throw.
  3. The chat pump owns exactly one `AbortController` per turn (`beginTurn` / `activeTurns` in `chat-handlers.ts`) and passes its `signal` into `runAskTurn`, which attaches `abort → agent.abort()` and detaches in `finally`. A user Stop, the pump's `ASK_PUMP_TIMEOUT_MS` and normal completion all route through that controller. `abortPiDesktopRun()` is **not** called by the pump any more — it belongs to the unwired `PiDesktopAgent` half, and would abort a run the Ask loop never starts.
- **`RUN_TIMEOUT_MS` is a whole-run budget (10 min), not a per-call one.** It used to hold `DesktopAgent`'s `llmTimeoutMs` (60s, a *single model call* inside the old loop), which aborted legitimate multi-step work. Pi has no `maxSteps` equivalent of `DesktopAgent`'s 25-step cap, so this and the model's own stopping are the only ceiling; enforce anything tighter at the consumer or via `finishTurn`.
- **The prompt's tool-priority order is a contract with `toolbox.ts`.** `prompt.ts` tells the model to prefer structured UIA tools; a tool added to the toolbox without a line there is a tool the model has no reason to reach for. `events.test.ts` holds the prompt's interpolated-bounds, screenshot-branch and strategy-change assertions.
- **The desktop agent is a process-wide singleton, deliberately — and today nothing constructs it.** `DesktopAgent` was a module-level singleton too, and so is this: `getPiDesktopAgent()` memoises one instance so the verifier baseline and the native handle tables are shared across runs, and `Agent.prompt()` throwing on a busy instance makes a single abort slot correct. But since the desktop family binds straight into the Ask `Agent`, **no production call site reaches `getPiDesktopAgent()`**; this class is the unwired half named in Ownership, and any work that wants the pixel verifier must either route Ask turns through it or lift the verifier into the Ask loop. Construction stays **lazy** either way (it opens the UIA facade and a tesseract worker) and so does the teardown — the runtime that *is* acquired lives behind `getDesktopRuntime()`.
- **One `Agent` instance processes one prompt at a time: `Agent.prompt()` throws if that instance is already processing**, and Pi's `toolExecution` defaults to `"parallel"`. There is no inter-agent delegation in this app — the single Ask `Agent` holds every family, and `runAskTurn` builds a fresh one per turn — so anything new that wants a concurrent run needs its own instance rather than a mutex around this one.
- Structural payloads for the renderer ride on `tool_execution_update` / `tool_execution_end` and `result.details`. Pi has **no** custom-event channel, so do not design around one.
- Logger name is `Pi`, registered to `LOG_PI` in `SUBSYSTEM_ENV_VARS` (`src/main/utils/logger.ts`). `logger.test.ts` fails if a `createLogger` call site is unregistered.
- **Teardown is `closePiDesktopAgent()` → `dispose()`, and it is a step in the quit list, not a fire-and-forget promise.** The agent owns two native resources — the adapter's tesseract worker and the UIA facade behind the a11y tree — and `DesktopAdapter.cleanup?()` is an **optional** member of the interface (`../desktop/types.ts`) precisely so a stub adapter in `toolbox.test.ts` need only the 18 tool methods. `main.ts` reaches it as the `pi-desktop-agent` step of `buildShutdownSteps()`, which `will-quit` runs under `event.preventDefault()` before `app.exit(0)`; each step is bounded by `SHUTDOWN_STEP_DEADLINE_MS` (2 s) and a failure is recorded rather than thrown, so a wedged native handle cannot strand the steps behind it. `closePiDesktopAgent()` clears the singleton *before* awaiting `dispose()`, so a run starting mid-teardown gets a fresh agent rather than one being dismantled underneath it.
- **The `main.ts` dynamic import does not keep Pi off the cold-start path, and must not be cited as if it does.** `npm run build` emits `INEFFECTIVE_DYNAMIC_IMPORT` for this module: `ipc/handlers.ts:8-9` statically import `chat-handlers` and `mcp-handlers`, `chat-handlers.ts:3` statically imports `ask-turn` from here, and `main.ts` imports `handlers.ts` statically — so Pi is in the main graph no matter how `main.ts` spells the import. The earlier claim that "a static import would put Pi's model provider on the cold-start path" is **not achievable** and has been removed from `src/main/AGENTS.md`. What genuinely defers the cost is **construction**: `getDesktopRuntime()` memoises, so the UIA facade and the tesseract worker are opened the first time a desktop tool is actually bound or called, not at boot. (`getPiDesktopAgent()` memoises the same way but today nothing calls it.) **The rule that survives is narrower and real: `main.ts` must never statically import Pi**, because the quit path depends on the runtime being cheaply absent when no task has run.
- **`abort.ts` exists so the hang regression can be tested against the shipped function.** `agent.ts` imports `electron`, both native adapters and `@earendil-works/pi-agent-core` at module scope, so a `// @vitest-environment node` test cannot reach a private helper there. `cancel.test.ts` **imports** `withAbort` and `sleep`; it used to re-declare both, which meant it kept passing after the real `withAbort` was deleted — a gate for the hang testing a mirror of itself. Never let a test here copy a subject; if it cannot import one, split the subject out Electron-free instead.
- Karpathy cap applies: max 50 lines per function. The long tools (`wait`, `file_operations`, `launch_app`, `hold_key`) keep their big branches in extracted module-level helpers for this reason — do not inline them back.

## Verification

- `npx vitest run src/main/services/pi/` — **109 tests across 12 files** (re-measured 2026-10-16). The original four are `provider.test.ts` (construction/lookup, including the env-read timing), `toolbox.test.ts` (the real 32 tools against stub adapters), `events.test.ts` (hand-built `AgentEvent`s through the bridge, plus the prompt's interpolated sections) and `cancel.test.ts` (the abort race and the toolbox's abortable sleep). `families.test.ts` holds the no-duplicate-name and label-coverage invariants; `ask-events.test.ts` the translator against a hand-built family index; `turn-record.test.ts` the trajectory builder. The remaining six are one per tool family under `tools/`, and each imports its production module. None of them construct an `Agent`, open a socket, or touch Win32 — and **nothing here constructs `PiDesktopAgent`**, which is the other reason its unwired half has stayed unnoticed.
- **All four files import production code.** `cancel.test.ts` imports `withAbort` from `./abort` and `sleep` from `./toolbox`; `events.test.ts` and `toolbox.test.ts` import their subjects directly. Mutation-checked this session: replacing `withAbort`'s race with a bare `return work` reddens `cancel.test.ts` (and hangs 5 s on the never-settling promise, which is the original defect). Before this, the file copied both functions and stayed green through that mutation.
- **`events.test.ts` builds a real `AssistantMessage` fixture, not a cast to `any`.** `AssistantMessageEvent` arms require `contentIndex` and a live `partial`; a `partial` needs `api`, `provider`, `model`, `usage` (with `totalTokens` and a four-field `cost`), `stopReason` and `timestamp`. Constructing it honestly is what makes the test fail when Pi grows a required field, instead of passing against a signature that moved.
- **`toolbox.test.ts` freezes the 32 tool names.** That list is the contract: it is now the only remaining record of the surface `desktop-tools.ts` used to hold. It also asserts the image-block screenshot, the omitted-when-false `verifies` flag, a real `details.status` per tool, and the never-throw path. It mocks `electron` for `clipboard`; `cancel.test.ts` mocks `electron` too, because importing `sleep` from `toolbox.ts` pulls the module-scope `clipboard` import with it.
- `npm run typecheck` and `npm run lint`. This folder adds **zero** warnings to the baseline (the run is 0 errors / 11 warnings, all of them in `src/main/services/desktop/**`). A file that needs an escape hatch declares it — `toolbox.ts` carries `no-explicit-any` disables with a reason — and an unused disable is itself an eslint warning, so delete it rather than leave it.
- **The `PiTool` interface is load-bearing and easy to break** — see Local Contracts. If typecheck suddenly reports ~30 `TS2322` on `execute`, someone has changed its declaration shape; restoring the method-syntax override is the fix, not widening each tool.

- **What is proven live, and what is not.** A real multi-step run against a live `BASE_URL` completed (a `get_window_info` task: 59 events, 1 tool call, 33 s), and the original 3-step hang was reproduced before the `abort.ts` fix. Still unproven by any test: a first real tool call against real Win32, and the `steer()`-based verifier feedback loop. `npm run dev` on a real desktop task is still the only gate for those — see root `AGENTS.md` ## Live Verification.
