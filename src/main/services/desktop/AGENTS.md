# src/main/services/desktop — DOX child contract

Parent: `../AGENTS.md` (agent-runtime rail); root `AGENTS.md` controls repo-wide rules. This folder is the repo's flagship capability and its densest native boundary.

## Purpose

Windows GUI automation: 32 LLM-callable tools over real Win32/UIA/OCR backends, gated by a per-tool danger policy with LangGraph HITL interrupts, reachable through two execution paths — a flat ReAct loop (`DesktopAgent`) and a hierarchical plan→execute→verify→recover subgraph. Owns input simulation, window management, accessibility-tree reads, screenshots, and the pixel/UIA verification of the agent's own actions.

## Local Contracts

- **THE SIX-COUPLED-EDITS RULE — adding one desktop tool requires six edits or the system breaks silently.** In order:
  1. `create<X>Tool` factory in `desktop-tools.ts`.
  2. Add the kebab name as a member of `DesktopToolName` (`types.ts:74-106`).
  3. Add a `DANGER_POLICY: Record<DesktopToolName, DangerLevel>` entry (`desktop-agent.ts:62-95`) — TypeScript exhaustiveness makes this the compiler-enforced step; skipping it fails `npm run typecheck`.
  4. Push the factory call into the literal array in `DesktopAgent.initialize()` (`desktop-agent.ts:136-170`); `bindTools` (`:190`) only sees this array.
  5. Add the tool's guidance line to the system prompt (`desktop-agent.ts:251-300`) or the model never prefers it over a screenshot.
  6. Teach `inferStatusFromTool` (`desktop-agent.ts:746-761`) — an unlisted tool reports `capturing` to the UI forever, silently.
  Also extend `index.ts` only if the tool is adapter-facing.
- **Registry truth: 32 tools.** 32 `export function create…Tool`, 32 `name: '…'` descriptors, 32 factories in the `initialize()` array, 32 `DANGER_POLICY` entries. `docs/desktop-agent.md:14` (26), `docs/desktop-agent-gap-analysis.md:11,53,846` (28/26) and `overall-architecture.md:128` (28) are all stale; correct them if you touch those files.
- **Tool descriptor shape** (`@langchain/core/tools`): `tool(async args => string, { name, description, schema: z.object({...}) })`, wrapped by `createXTool(adapter)`. Canonical example `desktop-tools.ts:19-52`; the contract is `desktop-tools.ts:1-8` imports plus one try/catch per tool.
- **Two entry paths, one policy.** Flat: `DesktopAgent.executeTaskStream` (`:200`) → `runReactLoop` (`:328`), with an abort-recovery variant (`:646`). Hierarchical: `desktopSubgraph` (`desktop-subgraph.ts:705`) via `executeDesktopSubgraph` (`:712`); `executeSubtask` node (`:195`) drives the flat loop per subtask (`:218`). Both are reached only from intent `"desktop"` (`../langgraph/research-agent.ts:377` valid intents, routing `:408-417`, node call `:1089`). HITL from here surfaces through the parent doc's streaming contract.
- **Three native backend families — do not add a fourth mechanism.** (1) koffi FFI: `input-simulation.ts` loads `user32.dll` (`:167`) and `shell32.dll` (`:177`), binds SendInput/SetCursorPos/GetForegroundWindow/GetWindowTextW/GetWindowRect/EnumWindows/SetForegroundWindow/SetWindowPos/ShowWindow/PostMessageW/SendMessageW/IsIconic/IsWindowVisible at `:170-197`, plus BlockInput/GetKeyState/IsProcessDPIAware/GetDpiForWindow/GetSystemMetrics/SystemParametersInfoW/MonitorFromPoint/GetMonitorInfoW at `:984-1005`. (2) libwin32: `GetWindowThreadProcessId` (`:958`) and token elevation (`:959`) only — DPI/input-blocking are explicitly noted as koffi-only (`:961`). (3) `node-winautomation` COM for UIA (`uia-native.ts:3`), facade `accessibility-tree.ts:32`. Capture is Electron `desktopCapturer` (`screenshot-capture.ts:26`); OCR is `tesseract.js` (`windows-adapter.ts:5,14`).
- **The shipped accessibility path is native COM, not PowerShell UIA.** `docs/desktop-agent.md`/`-gap-analysis.md` (`:11,49,62,657`) and `overall-architecture.md:128` claim PowerShell UIA; they are wrong. `uia-wrapper.ts` (the PowerShell UIA path) is dead with zero importers — do not revive or cite it.
- **Danger policy actual severity: 29 safe / 2 reviewable / 1 dangerous.** `drag` (`:83`) and `execute_command` (`:88`) are `reviewable`; `close_window` (`:89`) is the only `dangerous`. The docs' "24 of 26 safe" is wrong. Anything not in the map defaults to `reviewable` (`:418`).
- **`file_operations` overrides its own level per action** (`desktop-agent.ts:421-430`): `delete_file` → `dangerous`, `write_file`/`copy_file`/`move_file` → `reviewable`, the rest → `safe`. Adding an action to that tool's enum (`desktop-tools.ts:656`) without updating the override silently downgrades it to `safe`.
- **HITL**: any level `!== 'safe'` interrupts (`desktop-agent.ts:438-469`) with a `desktop_confirmation` payload (`:440-448`). Deny pushes both a ToolMessage and a HumanMessage instructing "Do NOT attempt this action again" (`:455-462`) then continues the loop; approval logs and executes.
- **`execute_command` has no allowlist.** It runs arbitrary strings through `exec` with `shell: 'powershell.exe'` and a 30 s default timeout (`desktop-tools.ts:809-814`, factory `:798`). Its only guard is the `reviewable` HITL gate. Never lower that level, never add a second command tool without a filter.
- **Coordinates are clamped to the primary `workArea`, not to the screen** (`windows-adapter.ts:19-28`), applied at `:49,59-60,73,129,134,139`. `input-simulation` also exposes `clampToPhysicalScreen`/DPI helpers — the adapter clamp is the authoritative one for tools.
- **Two verifier levels, and only one is automatic.** In-loop `GroundTruthVerifier` (`verifier.ts:46`, thresholds `:8-9`) runs ONLY when `dangerLevel === 'dangerous'` (`desktop-agent.ts:543-573`) and injects a corrective HumanMessage on hard-reject or score < 0.5. The subgraph `desktop-verifier.ts` (912 lines) is the real one: parses NL postconditions (`:16`), UIA-first with a deterministic window fast path (`:753-830`), screenshot-fallback weights window 0.4 / pixel 0.4 / OCR 0.2 (`:449-451`), hard-reject below 0.3 (`:8`, `:627`), wired at `desktop-subgraph.ts:371-431` → `desktop-recovery.ts` (`:436-494`). `verifyBrowserDelegation` (`desktop-verifier.ts:855`) is dead — called by nothing.
- **Planner and delegation.** `DesktopPlanner` (`desktop-planner.ts:90`) decomposes the task into `Subtask[]` (`types.ts:202-211`: `id`, `description`, `precondition`, `postcondition`, `maxSteps`, `status`, `requiresBrowser`); `isBrowserTask` (`:86`) is the heuristic that makes `executeSubtaskRouter` (`desktop-subgraph.ts:555`) branch to `delegateToBrowser` (`:267`, registered `:645`), which calls `executeBrowserSubgraph` (`:9`). There is no delegate-to-document node. Retrieval feeds the plan through `desktopMemory` (`retrieve:22` limit 3, `store:45` → `db.saveTrajectory`, `recordFailure:61`, `formatContext:83`) — table ownership is the `../database/AGENTS.md` contract, not this one.
- **`wait` is the only synchronisation primitive exposed to the model**, with three condition types `duration | window_change | text_appears` (`desktop-tools.ts:362`, evaluation `:304-330`). Anything else that needs settling uses the fixed 50 ms inter-tool delay (`desktop-agent.ts:576`).
- **Progress status is a closed union** — `'capturing' | 'clicking' | 'typing' | 'scrolling' | 'dragging' | 'key_combo' | 'window_management' | 'complete' | 'error'` (`desktop-agent.ts:100`), emitted per tool (`:578-585`) and at completion (`:589-596`). A new status means a new `inferStatusFromTool` branch AND renderer support; the loop's LLM timeout path is `invokeWithTimeout` (`:763`) with an abort-recovery loop variant (`:646`).
- **`DesktopAdapter` (`types.ts:46-70`, 18 methods) is the seam between tools and Win32.** Adding a method means three coupled edits: the interface, `WindowsDesktopAdapter`, and the `input-simulation` function behind it — then a tool, only if it is LLM-facing. Tools receive the adapter as a constructor argument (`createClickTool(adapter)`) or nothing when they shell out (`createLaunchAppTool()`); the existing lazy-`await import('./input-simulation')` call sites listed under Work Guidance are legacy, not a pattern to extend.
- **Two handle tables are the agent's only memory — both are process-local integers.** Window handles: `hWndMap` / `hWndCounter` (`input-simulation.ts:160-162`) mint `"1"`, `"2"`, … which `get_window_list` renders as `[N] "title"` (`desktop-tools.ts:441,451`) and every window tool re-resolves through `resolveHwnd` (`:763`, used `:775,785,795,804,813`); stale handles fail with the "may be invalid or the window may no longer exist" strings (e.g. `:551,712`). UIA element handles: `elementHandleMap` / `elementHandleCounter` (`uia-native.ts:35-42`), resolved by `resolveElement` (`:44-47`), cleared wholesale by `clearElementHandles` (`:49`). Consequence: the model must re-list windows or re-search elements after any UI change; never cache a handle across subtasks.
- **Screenshots are Electron-native first, PowerShell second.** `captureAllScreens` uses `desktopCapturer.getSources` (`screenshot-capture.ts:26`), throws when it returns zero sources (`:33-34`), and on any failure falls to `fallbackPowerShellCapture` (`:70`, invoked `:57`) which runs a System.Drawing script (`:85-101`) through `powershell.exe`, once plus one retry (`MAX_FALLBACK_ATTEMPTS = 1`, `:10`, loop `:71`, final give-up `:141`). The path is base64-encoded before embedding (`:75`).
- **DPI, blocking and elevation guards exist and must be respected** (`input-simulation.ts`): `blockInput:1013` + `withInputBlocked:1276` (BlockInput needs admin, failures ignored `:1281`), `isProcessDpiAware:1066`, `getDpiForWindow:1081`, `getDpiScaleFactor:1124`, `physicalToLogical:1137` / `logicalToPhysical:1149` / `clampToPhysicalScreen:1161`, `isWindowElevated:1174` (GetWindowThreadProcessId + OpenProcess + GetTokenInformation, `:1172`), `isWindowProtected:1198`, `getMonitorInfoForPoint:1222`. Elevated/protected targets are why `close_window`/`minimize_window` fail with the sandbox wording above — do not convert those into retries.
- **Lifecycle**: `DesktopAgent.closeSession` (`:788`) and `cleanup` (`:810`) are the only teardown hooks; they must release `inputSim.cleanup()` (`input-simulation.ts:929`) and the UIA facade (`accessibility-tree.ts:320-327`, which fires `cleanupNativeUIA` `uia-native.ts:500`). `WindowsDesktopAdapter.cleanup()` (`windows-adapter.ts:116`) terminates the tesseract worker.
- **Cold-start path is an optimization contract.** `executeTaskStream` skips the initial screenshot for simple window tasks via a regex on the task text (`desktop-agent.ts:216-217,239-241`, ~1 s saved) and degrades to a text-only first message when capture fails (`:234-238`); the first message is multimodal only when a data URL exists (`:243-248`). Preserve both branches — dev-only "always screenshot" tweaks blow the <500 ms budget.
- **Tools never throw.** Every catch returns a string `"<Verb> failed: <msg>"` (`desktop-tools.ts:42,62,105,125,145,167,…`) so the model can read and recover. Screenshot is the one object return: `{_type:'screenshot_result', description, image}` (`:11-15`, `:34`), detected at `desktop-agent.ts:490` and converted to a multimodal ToolMessage (`:528-540`). Schema errors are rewritten into a corrective `SCHEMA ERROR:` string (`:503-510`); an unknown tool name returns `Error: Unknown tool …` (`:481`). Do not replace these with exceptions.

## Work Guidance

- Zod only at the LLM boundary; `.describe()` on every field — descriptions are the model's only schema documentation. Argument-free tools still use `schema: z.object({})` (`desktop-tools.ts:196,214,452,477,699`).
- Naming: factory `create<X>Tool`, kebab-case filenames, `export class X` with `export const x = new X()` on the file's last line (`desktop-planner.ts:304`, `desktop-verifier.ts:912`, `desktop-recovery.ts:241`, `desktop-memory.ts:165`).
- `createLogger('PascalName')` at module scope; never `console`. Only `DesktopAgent|DesktopTools|DesktopVerifier|DesktopPlanner|DesktopMemory|DesktopRecovery|DesktopSubgraph` are registered in `SUBSYSTEM_ENV_VARS` (`src/main/utils/logger.ts:76-82`); `InputSimulator`, `UIANative`, `AccessibilityTree`, `ScreenshotCapture`, `WindowsDesktopAdapter`, `GroundTruthVerifier` are NOT registered, so their `info`/`debug` silently vanish in production. Add a `LOG_DESKTOP` entry when you need them.
- Preserve the lazy `await import('./input-simulation')` inside handlers (`desktop-tools.ts:244,299,432,674,920,950,974`) and the lazy `child_process`/`fs` imports (`:802,1004`) — module-load-time FFI is what makes this subtree survivable on non-Windows and in the Vite graph.
- Subgraph nodes: wrap in `traceNode` (`desktop-subgraph.ts:114`), return `Partial` state (never mutate), accumulate arrays through `appendArray` (`:16`) reducers. Node state is typed `any` here — the newer convention in `../document/` (`typeof X.State`) is preferred for new nodes; do not retrofit the desktop graph wholesale.
- Prompt maintenance lives in one place: `desktop-agent.ts:251-300` (tool priority order `:264-274`, guidelines `:276-300`, strategy-change rule `:302`). Tool-count or capability changes must edit that string in the same pass.
- `ui-detector.ts` is byte-identical to `../document/ui-detector.ts` (differs only at `:3`, `SOURCE_NODE`) and a third copy lives in `../browser/`; all three are dead. If you adopt it, collapse to one module with a `sourceNode` argument first; do not add a fourth copy.
