# src/main/ipc — IPC surface contract

Parent rails: `../../../AGENTS.md` (repo) and `../AGENTS.md` (host shell). This doc owns the whole IPC surface **including `src/preload/`**, because a channel is only meaningful across both trees. `src/preload/` has no doc of its own; do not create one.

## Purpose

Own every `ipcMain.handle` ↔ `ipcRenderer.invoke`/`.on` bridge: channel naming, request validation, error shape, main→renderer push plumbing, and the registry maps a handler author must touch. Renderer business logic and main-process boot ordering are out of scope here.

## Local Contracts

- **Channel naming is `namespace:camelCaseVerb`.** Namespaces in use: `app`, `window`, `command`, `url`, `file`, `apps`, `dialog`, `debug`, `chat`, `mcp`, `browser`, `api-config`, `settings`. Known three-segment exceptions: `file:everything:status` (`handlers.ts:371`), `desktop:screenshot:capture` (`preload.ts:74`). Do not add a third segment casually.
- **Every channel is four hand-synced sites**: channel string in `preload.ts` → `ipcMain.handle` in `src/main/ipc/*` → call site in the renderer → type at `src/renderer/types/electron.d.ts`, which is `typeof electronAPI` re-exported from `preload.ts:397`. There is no schema and no codegen; the compiler will not catch a missing site.
- **Registrars**: `registerIPCHandlers()` (`handlers.ts:17`) ← `main.ts:130`, and it calls `registerChatHandlers()` (`:18`, defined `chat-handlers.ts:199`) + `registerMCPHandlers()` (`:19`, defined `mcp-handlers.ts:7`). `registerApiConfigHandlers()` (`api-config.ts:143`) ← `main.ts:133` and `registerBrowserHandlers()` (`browser-handlers.ts:9`) ← `main.ts:139`. A new handler file needs its own `registerXxxHandlers()` wired into one of those three call sites — `ipcMain.handle` throws on duplicate registration, so registrars must stay idempotent.
- **Validation is split and asymmetric, and there are three shared validator modules.** `validateUrl`/`validatePath` exist **only** as local functions inside `handlers.test.ts:6,48`; most production handlers check logic inline. The rules that live in their own Electron-free module and are imported by a handler are `isCommandSafe` (`command-guard.ts`, called at `handlers.ts:166`) and `checkBaseUrl` (`api-config-guard.ts`, called by `api-config.ts` before `api-config:save` persists a `baseUrl` and before `api-config:test` fetches it with a key attached — main used to fetch any renderer-supplied URL, which is the same bypass class as `command:execute`). The third module is `file-guard.ts` (`isSafeSearchQuery`, `isUsablePath`): `file:search` was validated only in the preload layer and `file:revealInFolder` reached `shell.showItemInFolder` with no check at either layer, so a direct `ipcRenderer.invoke` — or a DevTools holder — shipped raw strings to `es.exe` and to the shell. Several tests now import production code (`command-guard.test.ts`, `mcp/client-contract.test.ts`, `chat-cancel-turn.test.ts`, `api-config-guard.test.ts`, `file-guard.test.ts`, `windowManager.test.ts`, `handlers-failures.test.ts`), which is the pattern `handlers.test.ts` still does not follow. Actual sites:

  `command:execute` is the most dangerous surface in the repo. Main now re-checks the same four keywords, which closes the `ipcRenderer.invoke` and DevTools bypasses, but the blocklist itself is trivially bypassed (`Remove-Item -Recurse`, aliases, encoded commands) — treat the channel as arbitrary execution. If you tighten validation, tighten both layers in the same change. **It is also the one `exec` in the tree that runs a real OS child with no inherent bound, so both bounds are explicit** (`handlers.ts`): `timeout: 30000` and `maxBuffer: 10 * 1024 * 1024`. Node's `exec` defaults are `timeout: 0` — *no timeout*, i.e. a command that never exits holds its shell and this IPC call open forever with nothing to kill it — and a 1 MB buffer, which turns a chatty command into a truncation error. A new `exec` in `src/main/**` with neither is a defect on arrival; the sibling bounds are `utils/esRunner.ts` (10 s / 10 MB) and `services/pi/toolbox.ts` (`execute_command`, 30 s default / 10 MB).
- **Three error idioms coexist; pick deliberately.** (a) Result envelope `{ success, output?, error? }` with the throw swallowed into `log.error` — `command:execute` (`handlers.ts:165`), `url:open` (`:185`), `file:open` (`:201`), `chat:initialize` (`chat-handlers.ts:225-256`); (b) re-thrown across IPC — `window:setMode` (`handlers.ts:56`), `file:search` (`:312`), `browser:executeTask` (`browser-handlers.ts:45`); (c) swallowed with a fallback value — only `window:getHeight` still does this, returning `600` (`:140`). `window:getMode`/`toggleMode` used to return `'compact'` on a thrown error and now re-throw (`:72`, `:82`): a fabricated mode is not a neutral default, because the renderer lays the palette out for whatever it is told, so the old fallback made an ordinary read indistinguishable from a real compact window. `dialog:openFile`/`openFolder` (`:395`, `:418`) are a fourth, deliberate shape — `{ path }` on success, `{ cancelled: true }` when the user dismissed it, `{ error }` when the call threw, which used to be reported as a cancel. Narrow with `err instanceof Error ? err.message : err`.
- **Push plumbing**: main uses `webContents.send`, preload subscribes once at module scope and re-dispatches a DOM `CustomEvent` — `window:shown` → `electron-window-shown` (`preload.ts:52-54`), `window:will-hide` → `electron-window-will-hide` (`:57-59`), `window:modeChanged` → `electron-window-mode-changed` (`:62-64`), and `window:modeSettled` → `electron-window-mode-settled` (`:69-71`, payload `{mode, height}` measured by main **after** the height tween finishes — `modeChanged` deliberately arrives early so the renderer can lay out, and this is the fact that the geometry now holds). Adding a `window:*` push costs three sites, not five: main send, preload dispatch, consumer. **One channel runs the other way and carries no payload at all**: `window:animationFrame` (`ipcRenderer.send` at `preload.ts:191` → `ipcMain.on` at `handlers.ts:160` → `windowManager.onAnimationFrame()`), the page's report that a frame happened, which is what paces the height tween. It takes no argument, so it cannot set geometry, and because it is neither an `invoke` nor an `ipcRenderer.on` it appears in none of the four drift greps below — count it separately when reconciling the surface. It *is* on the bridge (`electronAPI.window.animationFrame`) and is declared in the stale duplicate too (`src/renderer/types.d.ts:93`), so it is a five-site channel: preload string → `ipcMain.on` → call site at `src/renderer/hooks/useWindowTween.ts:29` → `typeof electronAPI` → `types.d.ts`. Streaming channels bind inside `electronAPI` closures instead. Every `onXxx(cb)` **must** return an `ipcRenderer.removeListener` unsubscribe (`preload.ts:291-376`); the renderer relies on it for cleanup.
- **Every push of a turn is stamped `{threadId, sessionId, seq}`** by the `send` closure that `beginTurn` returns (`chat-handlers.ts`), which is why the send handler calls `send(...)` rather than `event.sender.send(...)` — a new push site that bypasses it is silently unattributable. The envelope is additive and defined in `src/shared/ipc/turn.ts`. The `chat:thinking-step` payload is `ThinkingStep` from `src/shared/ipc/thinking-step.ts` — imported by both the pump and `useChatSession.ts`, because it was previously declared in both places and a `label` field added on one side would have been invisible to the other. There is now exactly **one** chat pump (`chat:sendStreamMessage`) and it stamps; `chat:resumeGraph` and `chat:sendMessage` are both deleted. The one intentionally unstamped send on a turn channel is the pre-turn failure fallback, which must still deliver a terminal chunk when no turn exists. A second push never goes through `beginTurn` at all: **`chat:sessions-changed`** carries `ChatSessionSummary[]` (`src/shared/ipc/sessions.ts`) whenever the visible session list can change, is published by `langChainAgent.setSessionsChangedNotifier` from the agent's own mutation sites, and re-published once by `chat:initialize` so the renderer never fetches the list — that fetch, wrapped in `useEffect(loadHistory, [loadHistory])`, was the unbounded `chat:listSessions` loop. It is not turn-scoped, so it has no `threadId`/`seq` and the renderer must not run it through `acceptEvent`. Proven by `chat-sessions-push.test.ts` (the wire) and `services/langchain/sessions-publish.test.ts` (the real agent publishes on mutation, and not on a create that leaves the list unchanged).
- **Turn identity is announced, not inferred.** `chat:sendStreamMessage` registers its `AbortController` in `activeTurns` (`chat-handlers.ts`) keyed by the per-turn `thread_id` and immediately pushes `chat:turn-started {threadId}` **before the first token**, because the renderer otherwise cannot name the turn it is asking to stop. `chat:cancelTurn {threadId}` marks `cancelledByUser`, aborts, and the pump ends as a **completed** turn (`{chunk:'', isComplete:true}` with no `error`) — deliberately distinct from the timeout path, which sends `isComplete:true` **plus** an `error` string the user is told to retry. Cancelling a thread that is not running returns `{success:true}` as a no-op; a non-string or empty `threadId` is rejected.
- **The pump owns the turn's cancellation, and threading it into the loop is not optional.** `beginTurn()` creates one `AbortController` per turn, the `chat:cancelTurn` handler and the `ASK_PUMP_TIMEOUT_MS` timer both abort it, and its `signal` is passed into `runAskTurn()`, which attaches `abort → agent.abort()` and detaches in its own `finally`. `withAbort`/`withTimeout` (`../services/pi/abort.ts`) then settle the await even if the model never answers — which is the whole point: dropping the signal, narrowing the abort to `cancelledByUser`, or letting the timeout timer survive the `finally` reintroduces the 2026-10-15 hang. `abortPiDesktopRun()` used to be the pump's cancel path; it is **no longer called from here** because the desktop tools now run inside the Ask `Agent` rather than a second singleton — see `../services/pi/AGENTS.md`.
- **The approval gate is deleted; there is no resume channel.** `chat:resumeGraph` and `desktop:confirmation-request` are removed along with `src/shared/ipc/hitl-decision.ts` and the confirm dialog. The desktop agent runs every tool without prompting — see `../services/desktop/AGENTS.md` for the resulting security posture. Do not reintroduce a resume path without deciding where the paused-turn payload is read: the previous implementation read `getState().values.__interrupt__`, which LangGraph never populates (it is `getState().tasks[].interrupts`, and the `invoke`/`stream` return value), so the dialog was unreachable in production. `chat-cancel-turn.test.ts` still imports the production registrar and asserts the cancel envelope.
- **Label routing is derived from the tool, not announced by a classifier.** `chat-handlers.ts` keeps no node lists and no label map: it receives `AskStreamEvent`s from `pi/ask-events.ts`, which reads the label from `pi/families.ts`'s `buildFamilyIndex(toolboxes)`. The index maps tool name → family → `AgentLabel`, and the translator emits `chat:agent-change` on the first tool of a turn. Before any tool runs the label is `IDLE_AGENT_LABEL` (`"General"`). Adding a family is one row in `families.ts`, one guidance string in `pi/ask-prompt.ts`, and one bind line in `pi/ask-tools.ts`; `families.test.ts` asserts every label the map can emit is one `AgentIndicator.tsx` renders, and `buildFamilyIndex` throws if two families claim the same tool name.
- **The pump has a database side effect, and it is deliberately unawaited.** On each of the three in-try exits — normal completion, `ASK_PUMP_TIMEOUT_MS`, and a user Stop — `chat:sendStreamMessage` builds a `TrajectoryRecord` with `pi/turn-record.ts` and calls `saveTrajectory` **after** the terminal chunk has gone out, with `void … .catch()` inside a `try` that swallows to `log.debug`. A lost record must never cost the user their answer, and the database may never have opened (boot degrades to a warn). The thrown-error path writes nothing, because the step accumulators are `try`-scoped. A user Stop records `success: false` even though the transcript ends the turn as completed — recording it as a success would inflate the only number an evaluation reads. `getDatabaseManager` is imported from `database/database-manager.ts` **directly**, never from the `services/database` barrel: that `index.ts` re-exports row interfaces as values and importing it fails the bundled main build with five `Missing export` errors.
- **The terminal chunk's `metrics` carries only what main measured**: `durationMs` and `model`. It used to carry `tokensUsed` derived from `fullResponse.length / 4`, a fabricated `0.3`/`0.7` input/output split, and an `estimatedCost` from a hard-coded `0.0002` constant — all rendered as a token/cost breakdown. `TaskMetrics.tokensUsed`/`estimatedCost` are optional in the renderer type and every row that needs them is conditional. When Pi's usage record is plumbed here, add the real fields; do not restore an estimate.
- **`chat:initialize` is the one channel whose failure needs a restart, so its envelope carries `retryable`** (`chat-handlers.ts:225-256`). Ready: `{ success: true, ready: true }`. Model client absent: `{ success: true, ready: false, retryable: false, error }`, where `error` names the fix (`API_KEY`, or `MODEL`/`BASE_URL` when a key exists) — `langChainAgent.initialize()` latches `isInitialized` (`src/main/services/langchain/agent.ts:119-130`), so a second call cannot pick up a key that appeared after boot. `initialize()` throwing: `{ success: false, ready: false, retryable: true, error }`. The renderer reads all three fields — it shows `error` verbatim and offers "Try again" only when `retryable !== false` (`src/renderer/hooks/useChatSession.ts:363-377`); `error` was previously built and discarded. Never return `ready: false` without a `retryable` value and an actionable `error`: an unadorned `ready: false` renders a retry button that can only fail again. The preload binding is a bare `ipcRenderer.invoke` (`preload.ts:277`), so `typeof electronAPI` gives the renderer `any` here — no type catches an envelope edit; the four-site sync is by hand.
- **Cross-namespace registration is a live landmine**: `browser:initializeAgent` (`mcp-handlers.ts:147`) and `browser:getStatus` (`:162`) are registered by `registerMCPHandlers`, not by `registerBrowserHandlers`. Grep `ipcMain.handle` across all six registering files before assuming where a `browser:*` channel lives.
- **`src/preload/types.d.ts` is no longer a duplicate — it is a three-line re-export** (`export type { ElectronAPI } from '../renderer/types'`). Never add declarations to it. The hand-maintained duplicate that still bites is `src/renderer/types.d.ts`, which declares its own `ElectronAPI` and its own `Window.electronAPI`, so a channel already named there needs five edits, not four — see `src/renderer/AGENTS.md`. The single live bridge is `export const electronAPI` (`preload.ts:155`) exposed via `contextBridge.exposeInMainWorld('electronAPI', electronAPI)` (`:389`). Preload runs sandboxed as compiled CJS and cannot import from `src/main`; `WindowMode` is re-declared locally (`preload.ts:47`).
- The `// #region agent log` block (`preload.ts:6-42`) is debug scaffolding: `logToServer` is inert unless `LOG_PRELOAD=true` and refuses any endpoint that is not `127.0.0.1`/`localhost` (`:18-20`). Do not extend it into a feature.

## Work Guidance

- Add a channel in one pass across all four sites; name it `namespace:camelCaseVerb`; return either a plain value or `{ success, error? }` — never a bare `throw` for a channel the renderer does not wrap.
- Keep handlers thin and under 50 lines (root rail); delegate to `src/main/services/*`.
- Validate in main, not only in preload — main is the only boundary the sandbox actually guarantees.
- Do not add a `browser:*` handler to `mcp-handlers.ts`; consolidate new ones in `browser-handlers.ts` and treat the two existing stragglers as debt to move deliberately.

## Verification

`node_modules` is installed in this checkout, so `npm run typecheck`, `npm run lint` and `npm run test` all run here — a fresh clone needs `npm install` first, and `../AGENTS.md` Verification carries the current gate results. **`handlers.test.ts` verifies a copy, not the shipped surface**: it imports only `describe/it/expect` from vitest, imports nothing from production code, and re-declares `validateUrl`/`validatePath`/`isCommandSafe` inline (`:6,48,82`) — the first two do not exist in `handlers.ts` or `preload.ts`. A green `npm run test` proves almost nothing about IPC. **`command-guard.test.ts` is the exception and the pattern to copy**: it imports `isCommandSafe` from production, so it fails if the real guard is removed or weakened. `handlers-failures.test.ts` is the second test to drive this registrar itself: it registers `registerIPCHandlers()` against a mocked `electron` and calls the `window:getMode|toggleMode|setMode` and `dialog:openFile|openFolder` handlers it captured, so those five channels' failure shapes are real gates (mutation-checked — restoring `getMode`'s `return 'compact'` or the dialog's `{ cancelled: true }` catch reddens one test each). What remains untested is the rest of the ~60-handler surface — `app:*`, `apps:list`, `debug:log`, `url:open`, the `file:*` bodies beyond their guards, and `chat:initialize`'s envelope.

Real gate: `npm run typecheck`, then `npm run dev` and exercise the touched channel **as a user reaches it** — Alt+Space → palette → type/click/Enter — driving those keystrokes and clicks through `scripts/harness/` (root `AGENTS.md` ## Live Verification). A bare `ipcRenderer.invoke` or a `window.electronAPI` call in DevTools proves the handler runs; it does not prove the channel works, and it steps around exactly the guards this layer is judged on. Observe the outcome in the UI (`state`, `screenshot`) or in the written artifact, and report it. Re-run the drift greps below after any channel add/remove/rename; they are the only automated check this layer has.

`comm` the sets. Current counts: 62 handlers, 58 invokes, 14 preload listeners, 9 literal `.send(` senders (the turn pushes go through `beginTurn`'s `send` closure, so the union grep below is the real sender list). Every invoke has a handler. `chat:sessions-changed` is one of the senders and **not** a handler — it is a push with no `ipcMain.handle`, so adding one moves only the sender grep; check that list, not the invoke list, when reconciling a push.

**The sender grep must match two call forms now.** Chat/desktop pushes go through the `send` closure returned by `beginTurn` (`chat-handlers.ts`), so the historical `grep -rhoE "\.send\(\s*['\"][^'\"]+" src/main` sees **none** of them — it reported 6 senders when the true number was 11. Use the union instead, or the drift list will silently under-report every new chat push:

```bash
grep -rhoE "\.send\(\s*'[^']+'|[^a-zA-Z_.]send\(\s*'[^']+'" src/main | sed -E "s/.*'([^']+)'/\1/" | sort -u
```

**Drift list (broken bridges, not absent features — do not delete these handlers/listeners as dead code; they are half-wired and need a counterpart):**

- Handlers registered, unreachable from the renderer: `browser:initialize` (`browser-handlers.ts:10`), `browser:executeTask` (`:42`), `browser:cleanup` (`:152`), `mcp:initialize` (`mcp-handlers.ts:8`).
