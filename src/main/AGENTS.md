# src/main — Electron host shell

Parent rail: `../../AGENTS.md`. This doc owns the main-process shell only. The channel contract spanning `src/main/ipc/` and `src/preload/` is owned by `ipc/AGENTS.md`; agent runtime behaviour is owned by `services/AGENTS.md`.

## Purpose

Own the Electron main process: hard boot ordering, the frameless always-on-top palette window **and the lazily-opened settings window**, window-mode state, the system tray, the Alt+Space global hook, `preferences.json` persistence, the logging subsystem, and the Windows/file-search platform utilities. Initialise agent runtimes at boot and expose them through IPC — never implement agent behaviour here.

## Local Contracts

- **Boot order is a hard contract** (`app.whenReady()` at `main.ts:81`, running to `:172`): `initializePreferences()` → database → `initializeEs()` (Windows only) → `mcpService.initializeWithRetry()` (`:121`) → `Menu.setApplicationMenu(null)` → `registerIPCHandlers()` → `registerApiConfigHandlers()` → `registerSettingsHandlers()` → `registerBrowserHandlers()` → Playwright check (`execSync`, `:152`) → `registerGlobalShortcuts()` (`:159`) → `createTray()` (`:163`) → `createMainWindow()` (`:167`) → `void initializeAnimationPreference()` (`:172`). Window creation is last; IPC registration precedes it so the renderer never invokes an unbound channel. The animation read is fire-and-forget **after** the window, because `koffi` is a dynamic import and nothing on the first-paint path may wait for it — the height tween animates by default until it resolves.
- **ESM-only main process.** Keep the `globalThis.__filename`/`__dirname` polyfill (`main.ts:26-27`) and the post-build `import.meta.dirname` patch (`electron.vite.config.ts:11-29`); main builds as `formats: ['es']` (`:58`). Native modules must stay in `external` (`electron.vite.config.ts:61`). The polyfill comment at `main.ts:23` now says what it is for — "used by native `bindings` lookups"; the "required by better-sqlite3" wording it carried is gone along with that dependency, which was declared and imported by nothing.
- **Sandbox is on and non-negotiable**: `app.enableSandbox()` (`main.ts:61`) with `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true` (`windows.ts:87-89`); preload loads as compiled CJS `../preload/preload.cjs` (`windows.ts:90`, `electron.vite.config.ts:73`).
- **Window is frameless, transparent, always-on-top, skip-taskbar, non-resizable** (`windows.ts:65-92`; `skipTaskbar` `:76`); `resizable` stays on only in `expanded` — set by `applyModeConstraints` (`windowManager.ts:270`) — while `applyLockedModeSize` (`:310`) enables it just for the tween and locks it back off in the completion callback. Spawn size and position come from the work area, never the display frame (`windows.ts:55`).
- **The settings window is a second, ordinary `BrowserWindow`** (`settings-window.ts`), deliberately the inverse of the palette: taskbar-present, resizable, not always-on-top, opaque, frameless with a renderer-painted drag titlebar. It is created **lazily** (`openSettingsWindow()`, from the tray **Settings** item or `settings:open`), never at boot. Its `close` is a normal destroy (no hide veto), and it **cannot quit the app on its own**: the palette's `close` is vetoed to `hide()` (`windows.ts:129-137`) so it always stays in `BrowserWindow.getAllWindows()`, which is what keeps `window-all-closed` (`main.ts:192`) from firing. That invariant is the whole safety argument — if the palette ever gains a real close path, closing settings alone would quit the app. A live settings window must not outlive the main pid, so `destroySettingsWindow()` is the `settings-window` step of `buildShutdownSteps()` (`main.ts`, placed right after `tray`). `registerSettingsHandlers()` (`ipc/settings-handlers.ts`) owns the main-owned appearance: `settings:get`/`settings:set` read/write `preferences.json.settings` and push `settings:changed` to every open webContents; `settings:set` for `reducedMotion` also drives `setUserReducedMotion` (`utils/platform.ts`) so the height tween honours the override.
- **One emit point for `window:shown`, and the first show is not special.** The window's own `show` handler (`windows.ts:120-123`) hides the menu bar and sends `window:shown`; `showMainWindow()` (`:153-161`) no longer sends it, so every show — the boot `ready-to-show` (`:101-113`), the Alt+Space toggle, the tray, the `activate` path — announces itself exactly once. The renderer parks/restores keyboard focus and plays the surface reveal off that event, so a first show that skipped it left the launcher holding whatever caret Chromium picked. `ready-to-show` also calls `mainWindow.focus()`: a launcher takes the keyboard together with the screen. Measured consequence of the old gap plus a pid-only focus test in the harness: three real Escape presses hid nothing while a detached DevTools window (same pid) held the foreground.
- **Requested mode height is not realized height — and `useContentSize` is not the reason.** The realized CSS `innerHeight` sits a few DIP above what main asks (realized below Electron by DPI rounding / the transparent window's minimum frame), and it is **not a fixed constant across sizes**: measured live at dpr 1.25 on a fresh build, compact asks 72 → **74** (+2) and expanded asks 600 → **603/604** (+3–4). The older 100 → 103 figure predates the compact-height change; do not apply a blanket `ask + 3`. Because main's `getBounds().height` and the DOM agree exactly, there is no frame-vs-content error to fix: `useContentSize: true` was tried, measured byte-identical, and reverted. **Do not re-add `useContentSize` as a fix for it.** The harness encodes the measured values in `MODE_HEIGHTS` (`scripts/harness/driver.mjs`): compact 74, expanded 603. Re-time the tween (`MODE_HEIGHT_TWEEN_MS`) or re-measure the realized heights and the harness's `MODE_HEIGHTS` plus the selftest frame-smooth budget go out of step; rename or drop a `window:*` channel and the `electron-window-*` DOM events that `scripts/harness/cdp.mjs` records and `set_mode` waits on (re-dispatched from `window:shown`/`window:modeChanged`/`window:modeSettled` by `src/preload/preload.ts:49-70`) no longer fire. All three are a harness change as well as an app change — update `scripts/harness/{driver,cdp,cli}.mjs` and `scripts/harness/AGENTS.md` (the pinned-surface contract) in the same change.
- **Dev relaxations are env-gated; never widen them.** CDP `remote-debugging-port 9222` + `remote-allow-origins *` only under `NODE_ENV=development` (`main.ts:73-76`); detached DevTools only under `ELECTRON_VITE_DEV_MODE` (`windows.ts:105-107`).
- **Navigation lockdown**: `setWindowOpenHandler` → deny (`main.ts:323`); `will-navigate` allowlist hard-codes the dev origin and `file://` (`main.ts:328`). Any new dev port or origin must be added here or the window will not load.
- **Alt+Space requires two mechanisms on Windows.** A koffi `WH_KEYBOARD_LL` hook (`shortcuts.ts:104`) with 300 ms debounce (`shortcuts.ts:23,88`) and a 10 ms message pump that keeps it alive (`shortcuts.ts:139-145`), **plus** an in-window `WM_SYSCOMMAND`/`SC_KEYMENU` intercept because Windows reserves the combo (`hookAltSpaceInterceptor` `windows.ts:35-49`, installed at `:115`). The intercept is key-gated: it toggles only when `command === SC_KEYMENU && lParam === 0` (`windows.ts:43`), reading both arguments through `readWindowMessageArgument` (`:25-27`, Electron hands WndProc arguments over as little-endian buffers). Windows posts `WM_SYSCOMMAND`/`SC_KEYMENU` for **every** `Alt+<key>` accelerator with the character in `lParam`, so an ungated check tears the palette away during `Alt+Shift+T` and `Alt+Shift+M`. `globalShortcut.register('Alt+Space')` is the macOS/Linux path only, never a Windows fallback (`shortcuts.ts:179-192`). `Alt+Shift+M` (`shortcuts.ts:195`) is the only cross-platform shortcut.
- **The window hides; nothing closes it except the app's own Quit.** `close` calls `event.preventDefault()` **unconditionally** and hides when visible (`windows.ts:119-127`); the veto is unconditional because a close while hidden would destroy the window, fire `window-all-closed` (`main.ts:192`) and quit the app, leaving `mainWindow` a dead reference. The single escape is the module-level `isQuitting` flag set by `app.on('before-quit')` (`windows.ts:15-18`), which lets tray Quit (`tray.ts:49-52`) and `app:quit` (`handlers.ts:261`) through — so tray Quit works with the palette visible. `closed` nulls `mainWindow` (`windows.ts:129-131`); `hideMainWindow` is the direct hide path (`:153-161`). Both emit `window:will-hide` **before** hiding (`windows.ts:124,158`) so the renderer can park focus; `showMainWindow` emits `window:shown` (`:149`), which the renderer also uses to replay the palette reveal (`src/renderer/hooks/useWindowReveal.ts`). **Reveal is entrance-only by decision**: nothing in main ramps window opacity, and `hide()` stays instant — a global-hotkey launcher that fades out feels laggy, and delaying the hide would put the Alt+Space toggle in a race with itself. There is no `requestSingleInstanceLock` and no blur-to-hide — do not add either without a request.
- **Mode state persists through preferences, and sizing honours it.** `WindowMode = 'compact' | 'expanded' | 'custom'` (`windowManager.ts:8`) with pixel defaults in `MODE_CONFIGS` (`:20-36`). `setMode` sizes from `this.getModeConfig(mode)` (`:231`), never from `MODE_CONFIGS` directly, so `setMode('custom')` keeps the persisted `customDimensions` instead of snapping back to 800x480; it calls `savePreferences({ windowMode: mode })` (`:225`) and broadcasts `window:modeChanged` (`:235`) **before** sizing, then broadcasts `window:modeSettled {mode, height}` (`emitModeSettled`, `:334-340`) once the geometry is true — from the animated tween's terminal write, from the snap path, and from the already-expanded early return so a renderer that asked for the current mode is never left waiting. `setMode('expanded')` on an already-expanded window resizes nothing — user resizes survive — but re-applies the mode constraints and acknowledges before returning (`:157-164`).
- **The height change is one eased tween, paced by the page, and the mode's OS bounds go on only when it lands.** `animateWindowHeight` (`windowManager.ts:342`) interpolates height over `MODE_HEIGHT_TWEEN_MS` (`:41`, 180 ms) on `easeInOutCubic` (`:70`) — smoothstep, zero velocity at both ends — by elapsed time rather than a fixed pixel step, and it sets **height only** so the fixed top edge holds and the palette grows downward instead of being re-centred mid-flight (`repositionWindow` still runs at completion, and is a no-op on a width-locked window). **Main owns the curve; the page owns the clock.** `animateWindowHeight` writes nothing and starts a `TWEEN_STALL_SNAP_MS` (`:48`, 120 ms) timer; the tween advances only inside `onAnimationFrame` (`:382`), which `window:animationFrame` calls once per reported frame (`handlers.ts:155`, `src/renderer/hooks/useWindowTween.ts`). A main-process timer shares no phase with the compositor: `setInterval` measured 11 duplicate consecutive heights per transition and a self-rearming `setTimeout` measured 6 — the frame-paced version measures 0, with 11 distinct heights across 11 ramp frames (`scripts/harness/AGENTS.md`). **The curve was `easeOutCubic` until it was measured, and it failed.** Ease-out's velocity is maximal at `t = 0`, three times the average, so the first presented frame of a 103 → 603 px expand carried ~135 px (27% of the distance) and the page trace showed the card lurching then crawling the rest of the way; smoothstep puts 0.4% in that frame and peaks at 1.5× average mid-transition. `windowManager.test.ts` now pins the shape on a scripted clock (a real `setTimeout` makes the first frame arrive anywhere from 17 to 40 ms, which measures the scheduler, not the curve): first frame under 6% of the distance, last quarter under 20% (a linear curve is 25%), midpoint between 25% and 75% — three bounds that the old curve, a linear curve, and a stuck class each fail, in that order.
- **Tween mechanics the rest of the file depends on.** Each tick skips a rounded height it has already written; `finishTween` (`:411`) lands exactly one terminal write on the target and only then `emitModeSettled`, so the settled height is measured after the mode's real bounds are back on; the stall timer is the snap path when no frame arrives (hidden or occluded window, so rAF is throttled), which also covers a renderer that never reports; `cancelHeightTween` (`:442`) abandons an in-flight tween on a new mode change rather than stacking; deltas under 2 px, and every tween while `prefersWindowAnimation()` is false, jump straight to the target. Other assertions `windowManager.test.ts` holds against this real code: nothing is written before a frame is reported, at most one height per reported frame with no consecutive repeat, the snap when reports stop, `modeChanged` before the last write and `modeSettled` after it, a no-op mode change still acknowledging, and the resize authority — `clampExpandedHeight` (`:303`) bounds and rejects, `expandedHeightBounds` (`:288`) agreeing with what goes on the native window, and the width lock attaching to a recreated window (the old one-way boolean latch could not).
- **`TWEEN_MIN_BOUNDS`/`TWEEN_MAX_BOUNDS` (`:58`) exist because Windows honours a raised minimum by resizing immediately.** The expand path used to call `applyModeConstraints` *before* reading the tween's start height, so `setMinimumSize(800, ≈301)` on a window locked at its compact height snapped the native window ~200 px down the screen and the animation then eased from mid-air. `setMode` now calls `beginTweenBounds` (`:257`) first — which loosens min/max and attaches the width lock without moving the window — reads `getBounds().height`, and applies `applyModeConstraints` (`:270`) in the completion callback. `TWEEN_MIN_BOUNDS.height` must stay ≤ the smallest mode height (compact, now 72), otherwise that raised minimum bumps a compact window up before the tween reads its start. The stub in `windowManager.test.ts` emulates that Win32 rule, which is the only way a unit test can catch a call-order bug; reverting the order turns `expected 300 to be 72`.
- **Geometry is work-area math, in one place.** `getPaletteLayout(width, height)` (`windowManager.ts:126-135`) is the sole source of position: centred in `getWorkArea()` (`:96-99`), top edge at `PALETTE_TOP_OFFSET_RATIO` of the work-area height (`getWorkAreaTop` `:101-103`), available height from `getAvailableHeight` (`:106-108`), requested size fitted by `clampSizeToWorkArea` (`:111-120`), expanded ceiling `EXPANDED_MAX_HEIGHT = 1080` (`:83`). `createMainWindow` (`windows.ts:55`) and `calculateWindowPosition` (`windowManager.ts:510-518`) both call it, and nothing measures `bounds` — `bounds` and `workArea` disagree the moment a taskbar is docked top or left, which is what occludes the palette. Clamping is what keeps an 800 DIP palette on a 1024x768 @ 200% display from computing `x = -144` and bleeding off-screen.
- **Two sizing paths, split by mode.** `applyModeConstraints(window, mode?)` (`windowManager.ts:270`, public, `expanded` only) sets resizable, the min/max bounds produced by **`expandedHeightBounds()`** (`:288`, the one definition of the expanded floor and ceiling) and the width-lock listener (`attachResizeListener` `:170`, keyed on **the window instance** — a boolean latch could never be cleared, so the second palette window of a session got no width lock at all), and never touches the current height; `createMainWindow` calls it right after construction (`windows.ts:98`) because a session restored into `expanded` from preferences skips `setMode`, and without it an expanded window has no maximum height for the renderer's drag handle to push against. That handle drives `window:resizeHeight`, which now validates and clamps in main through **`clampExpandedHeight`** (`:303`, `null` for a non-finite request) and replies with the height it actually applied — it used to `setBounds` whatever number the renderer sent, which was the one IPC path that could size the palette past the work area (`handlers.ts:98`). `windowManager.test.ts` pins the clamp, the bounds agreement and the per-window attach. `applyLockedModeSize` (`windowManager.ts:310`, private, `compact`/`custom`) widens the bounds so the tween is not clamped away, animates, then hard-locks in the completion callback. `setCustomDimensions` (`:457`) persists the requested size and applies the work-area-clamped one; `getModeConfig` (`:477`) clamps in both of its branches (`custom` with stored dimensions, and the mode default); `applyModeToWindow` (`:524`) is the no-animation path and reaches geometry through `calculateWindowPosition` (`:510`).
- **`lifecycle.ts` is Electron-free on purpose, and that is the reason the split exists.** `main.ts` imports `electron` and `koffi` at module scope, so it cannot be imported under vitest — a lifecycle bug is therefore untestable where it lives. Splitting the policy (`runStep`, `createShutdown`) from the wiring (`buildShutdownSteps`) is what puts the four properties under test, and it mirrors `services/pi/abort.ts` for the same reason. Keep it Electron-free: importing `electron` here for a log line would move the untestable surface back.
- **Teardown is a real quit, not a log line.** `will-quit` calls `event.preventDefault()` **unconditionally** (`main.ts`), runs `buildShutdownSteps()` through `createShutdown()`, and only then `app.exit(0)`. It vetoes because Electron does not wait on a handler's promises — the previous handler fired three `.catch`-ed promises and returned, so `Cleanup complete` printed while every disposer was still in flight and nothing was ever *observed* to finish. `lifecycle.ts` is the owner of the four properties that make this safe, and it is Electron-free for the same reason `services/pi/abort.ts` is: `main.ts` cannot be imported under vitest, so the only testable place for a lifecycle bug is a module that does not pull `electron`/`koffi`. The order is `global-shortcuts` → `tray` → `settings-window` → `browser-agent` → `mcp` → `pi-desktop-agent` → `ipc-handlers` → `database`: the koffi message-pump interval is first because it is what holds the event loop open, IPC handlers are removed near the end to prevent new requests during final teardown, and the database is last so its `close()` flush captures writes made during teardown. `run()` is memoised, which is what makes the unconditional veto safe — a second `will-quit` joins the run instead of double-disposing already-torn-down native handles. **A new resource holder gets a step in this list in the same change that creates it**; `DatabaseManager.close()` shipped with zero callers for exactly that reason. `browser-agent` is also the browser subtree's release path (`cleanupBrowserAgent` calls `statefulBrowserAgent.cleanup()` and `browserSessionManager.closeSession()`), so there is deliberately **no** separate `browser` step — one owner, one call. **SIGTERM and SIGINT are handled** (`main.ts:40-58`): without handlers, Node.js exits immediately without cleanup when Docker/Kubernetes/systemd send SIGTERM or the user presses Ctrl+C (SIGINT). The handlers route into `app.quit()` so the normal Electron shutdown path fires `will-quit` and runs the ordered teardown. A `signalReceived` flag prevents re-entrant shutdown if multiple signals arrive.
- **The `will-quit` dynamic imports buy no cold-start laziness, and must not be cited as if they did.** `npm run build` emits `INEFFECTIVE_DYNAMIC_IMPORT` for `services/pi/agent.ts` (`main.ts:252`) and `services/langchain/agent.ts` (`main.ts:239`): `handlers.ts` statically imports `chat-handlers` and `mcp-handlers`, `chat-handlers.ts:3` statically imports `pi/ask-turn` → `ask-tools.ts` → `pi/agent.ts`, and `browser-handlers.ts:4` statically imports `langChainAgent`. Both are in the main graph either way. What is genuinely deferred is **construction** — `getDesktopRuntime()` / `getDesktopToolbox()` memoise, so the tesseract worker and the UIA facade are opened when a desktop tool is first bound, not at boot. (`getPiDesktopAgent()` memoises too, but no production call site reaches it — see `services/pi/AGENTS.md`.) The dynamic import is kept for the cheap exit (it doubles as the "was anything ever created?" test), not for timing. **`main.ts` must never gain a static import into Pi** — that is a real rule, because the quit path depends on the runtime being cheaply absent when no task has run; the dynamic import is not what protects the boot path.
- **`cleanupWindowsGlobalHotkey` releases the two handles that keep the process alive** (`shortcuts.ts:152-173`) — the 10 ms `messagePumpInterval` and the `WH_KEYBOARD_LL` hook — and `unregisterGlobalShortcuts()` (`:207-208`) is the only caller. It is the first shutdown step precisely because of this: a disposer ahead of it that throws would strand the interval that keeps the message loop running.
- **Logger registration**: use `createLogger('<Subsystem>')` at module scope. An unregistered subsystem inherits `globalLevel` (`logger.ts:51`, applied at `:106`/`:111`), which defaults to `error` in production, so its `info`/`debug` output silently never appears and no env switch can enable it. Add a `SUBSYSTEM_ENV_VARS` entry (`logger.ts:61-95`) for every new subsystem name — and note that `logger.test.ts` walks the tree and fails if a `createLogger('<Name>')` call site has no entry **or** an entry has no call site, so a deletion must remove its row in the same change.
- **Preferences merge is shallow spread** (`preferences.ts:121`): `savePreferences({ llm })` replaces the whole `llm` object, not its keys. `resetPreferences` (`:157`) is exported and called by nothing — do not cite it as a live path.

## Work Guidance

- New boot step: insert inside `app.whenReady()` (`main.ts`), keep the ordering contract above, and log through `createLogger('App')`. Anything on the critical path to first paint goes after `createMainWindow()` or is deferred.
- New shutdown step: add one entry to `buildShutdownSteps()` (`main.ts`) in the position the ordering contract requires, give it a `name` that reads in the log, and do not add a `try/catch` around it — `runStep` already converts a throw into a recorded `failed` outcome and continues. Only wrap a disposer that can *legitimately* be absent (the database is the precedent, because boot degrades to a warn).
- Non-fatal init only: DB (`main.ts:100-104`), Elasticsearch (`:109-113`) and MCP (`:121-124`) each wrap in `try/catch` and degrade to `log.warn`. Never `throw` from an init step — `uncaughtException` (`main.ts:32`) will swallow it and leave the app half-initialised.
- Cold start is the reason the boot order above is a contract. The root rail's <500 ms figure is **aspirational and has never been measured** — there is no instrumentation in this repo, so do not report it as a result. What is real: do not add synchronous `execSync` or blocking IO before `createMainWindow()`; `execSync('npx playwright install chromium')` (`main.ts:152`) is already the largest offender and sits after IPC registration. It is bounded by `timeout: 120_000` with `stdio: 'ignore'` so a network or npm hang cannot strand the boot indefinitely.
- New window mode: add a `MODE_CONFIGS` entry, extend the `WindowMode` union (`windowManager.ts:8`), give it a sizing path — `applyModeConstraints` if it is user-resizable, `applyLockedModeSize` if it is not — and **do not mirror the mode geometry back into `src/renderer/styles/` tokens**. Only the palette *width* is a shared token (`--container-command-palette`); the height tokens were deleted because a mirrored copy is how a fifth `MODE_CONFIGS` appeared inside a `CommandPalette` debug log, and main is the single owner of mode height. A consumer that needs the number reads it from `window:modeSettled`. Do not add a fourth magic size. Any new position or size number goes through `getPaletteLayout`/`clampSizeToWorkArea`, never off `screen.getDisplayNearestPoint(...).bounds`.
- New long-lived OS resource (a child process, an MCP server, a native handle, a persistent store) in this tree: register its release as a step in `buildShutdownSteps()` (`main.ts`) **in the same change that acquires it**, and give the step a `name` that reads in the log. `DatabaseManager.close()` shipped with zero callers for exactly this reason. A resource whose constructor opens something must be built into a local, published on success, and closed on throw — see `mcp/client.ts` for the shape and the reason.
- New main-process motion: gate it on `prefersWindowAnimation()` (`utils/platform.ts:120`), not on a hard-coded always. It caches the Win32 `SPI_GETCLIENTAREAANIMATION` flag (`:79`) read by `initializeAnimationPreference()` (`:92`) and fails open, because the CSS `prefers-reduced-motion` reset cannot reach `setBounds`. Any new FFI read follows the same shape: dynamic `koffi` import, `try/catch`, a default that keeps the app working, and never on the first-paint path.
- `windowManager` is a singleton (`windowManager.ts:536`); do not construct a second instance.
- Platform-branch every Windows-only path through `isWindows()` from `utils/platform.ts`; never test `process.platform` inline in this tree.

Real gate after any change here: `npm run typecheck`, then start `npm run dev` and walk the checklist **against the running app** (root `AGENTS.md` ## Live Verification). Use the harness wherever it can reach — `reveal` and `hide` are a real Alt+Space through the low-level hook and a real Escape, `set_mode` is a real `Alt+Shift+M`, `who`/`state` return the OS rect and the DOM height, `save_frame`/`selftest` trace the tween per frame — and hand-drive what it cannot (`Alt+Shift+T`, tray click/double-click/Quit, quitting and relaunching, taskbar docking, the Windows animation setting), naming which steps were hand-driven:
1. Alt+Space shows the palette; Alt+Space again hides it (both the hook and the `SC_KEYMENU` path must fire). Then press `Alt+Shift+T` and `Alt+Shift+M` — neither may toggle the palette or tear it away mid-keystroke (`lParam === 0` gate, `windows.ts:43`).
2. Close the palette while it is visible, then while it is hidden → the app stays alive in the tray **both** times (`close` is vetoed unconditionally, `windows.ts:119-127`). Tray click (`tray.ts:65`) and double-click (`tray.ts:60`) re-show it, and tray Quit (`tray.ts:49-52`) must work with the palette visible.
3. `Alt+Shift+M` toggles mode; switch to `expanded`, quit, relaunch — mode must come back from `preferences.json`, and the restored expanded window must carry the same bounds and height ceiling as a toggled one (`applyModeConstraints` at `windows.ts:98`), i.e. the renderer's drag handle cannot push it past the screen bottom.
4. Tray Quit exits cleanly — `isQuitting` (`windows.ts:15-18,120`) must get the destroy past the `close` veto — and the vetoed `will-quit` must run the whole step list before the process dies. **The assertion is the process tree, not the log:** capture `Get-CimInstance Win32_Process` for the app's pid tree, Quit, then confirm no MCP `node`/`npx` child and no renderer/GPU child outlived the main pid. The `Released <name> in <n>ms` lines prove the step ran; only the tree proves the child died. No harness verb may quit the app, so this one is hand-driven by definition.
5. Window must not be reachable from the taskbar/alt-tab (`skipTaskbar` `windows.ts:76`) and must stay above other apps. Dock the taskbar top or left and re-show: the palette must be centred inside the usable strip with nothing under the taskbar (`getPaletteLayout`, `windowManager.ts:126-135`).
6. Motion: summon with Alt+Space — the card fades and grows in over ~150ms and **hides instantly**. Toggle mode — the height eases out and settles inside ~200ms with the top edge held, no sideways jump at the end and no re-summon needed to finish it. Then turn on Windows Settings → Accessibility → Visual effects → "Show animations in Windows" **off** and repeat: the mode change must snap with no tween (`prefersWindowAnimation`, and the renderer's own reveal/`auto-animate` go quiet on the CSS media query).

No harness lives inside `src/`: the `TEST_DESKTOP_TOOLS=1` smoke harness (`utils/desktop-tools-test.ts`) and its `main.ts` hook were deleted at the Pi cutover along with the tools they exercised, and `ffi.test.ts` in `services/desktop/` is the only automated coverage of the native layer. Live driving is external and mandatory — `scripts/harness/` (`npm run harness:preflight`, `harness:selftest`, `harness:mcp`) reaches this process through real Win32 input plus the dev CDP port, so a main-process behaviour change is proved by watching the running app respond, not by a unit test.
