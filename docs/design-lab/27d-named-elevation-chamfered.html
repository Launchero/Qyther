27d · Named Elevation Chamfered — a machined edge where a radius would have been

Radius policy — `0px` throughout with a 10 px `clip-path` chamfer on the inner plates — the ladder, the dialog, the agent panel, the generative-UI frame, the steps, the tile, the command bar, the details block, the alert. Two consequences are stated up front: `clip-path` clips the element's own `box-shadow`, and this system's entire elevation language **is** a 1 px outer ring, so every chamfered plate has to wear its ring `inset` or lose its edge outright; and the card is not chamfered, for the same reason as 18d — a transparent frameless window's drop shadow is its only separation from the desktop.

Provenance — built on @rose-pine/palette 4.0.1 (MIT). Every hue in both token blocks is quoted verbatim from the shipped dist/css/rose-pine.css, whose :root prints --rp-base: #191724; --rp-surface: #1f1d2e; --rp-overlay: #26233a; --rp-muted: #6e6a86; --rp-subtle: #908caa; --rp-text: #e0def4; --rp-love: #eb6f92; --rp-gold: #f6c177; --rp-rose: #ebbcba; --rp-pine: #31748f; --rp-foam: #9ccfd8; --rp-iris: #c4a7e7; --rp-highlight-low: #21202e; --rp-highlight-med: #403d52; --rp-highlight-high: #524f67. The dark column is that variant; the light column is the dawn variant shipped in the same file (#faf4ed / #fffaf3 / #f2e9e1 / #9893a5 / #797593 / #575279 / #b4637a / #ea9d34 / #d7827e / #286983 / #56949f / #907aa9 / #f4ede8 / #dfdad9 / #cecacd), and moon (#232136 … #ea9a97) is shown in each banner as the third variant that costs nothing to carry. All three ship in one :root — the flip is a prefix re-point (--rp-base → --rp-dawn-base), not a value swap, so a .dark class on document.documentElement has to rebind names. Anything labelled DERIVED in the blocks is my arithmetic on those hexes, not a published token.

Why this one, structurally — Rosé Pine has the thing shadcn lacks and Qyther's surface ramp was invented to get: named elevation roles with semantic intent (base, surface, overlay, then highlight-low/med/high) instead of a generic card/popover pair doing double duty for "raised panel" and "floating panel". The second idea is borrowed from the same research pass, daisyUI 5.7.50 (MIT): it declares a -content foreground for every role — --color-info-content, --color-success-content, --color-warning-content, --color-error-content are all present in the shipped daisyui.css — so a theme swap cannot derive an illegible pairing. That is exactly the failure this repo guards with "a hue primitive is never a fallback for text". Here every role carries an explicit foreground in both themes.

The mapping problem, stated up front — the names are brand-shaped, not role-shaped: love, gold, rose, pine, foam, iris carry no opinion about primary, destructive or warning, so every mapping below is a claim and is commented as one next to the token. Three of them are forced by measurement, not taste: pine variant pine is 3.38:1 as text on base and 3.96 reversed, so it can only ever be a fill or a rule and foam becomes --primary; dawn love is 3.84:1 in both directions, so neither ink survives on it and the light column needs a DERIVED darkened red for --destructive; dawn subtle is 4.02:1 on base, under this repo's own AA floor, so light --muted-foreground is also DERIVED. Rosé Pine has no green, so --success collides with --primary in both columns — visible in the block, not hidden. And the ladder is not monotonic: in dawn, surface is lighter than base while overlay is darker, so the topmost named surface steps down in lightness — a port that raises surfaces by lightness has to decide whether to keep the names or the direction.

Type plan — neither package ships a type token: @rose-pine/palette is 15 colour declarations and daisyUI's --font-family defaults to the system stack. So UI text stays on the app's system stack (Segoe UI Variable Text / Segoe UI / Roboto, all OFL-free because nothing is vendored) and paths, numbers and key labels stay on JetBrains Mono (OFL). Scale is the app's own 12/13/14/16/20/28 with each rung keeping its existing line-height pair. That gap is the whole lesson: a palette built from colour ramps still has to author its type scale, its density and its focus contract — which is the difference between a theme and a design system.

Geometry — strict 4pt grid, radius 4 / 8 / 12 (daisyUI's own defaults are --radius-field:.25rem, --radius-selector:.5rem, --radius-box:.5rem, read from the shipped file), borders 1px with 2px for focus, per daisyUI's --border:1px, and its --depth:1 / --noise:0 pair respected in the negative: elevation here is a named highlight step plus a border, never a blurred shadow — --elev is a 1px ring, --key is a 1px offset, there is no blur() anywhere in this file. Each theme declares color-scheme so native scrollbars and form controls follow it.

  • Move 1 · steal the roles, not the namesAdd named elevation rungs to src/renderer/styles/tokens/colors.css as semantic-light primitives (--surface-1…3, --state-low/med/high) and re-point src/renderer/styles/semantic/theme.css's :root / .dark halves at them, so --card/--popover/--secondary/--accent stop doing double duty. Do not put love/gold/iris in the codebase — a brand name in a role slot is how --primary acquires a hue argument.
  • Move 2 · the -content law, mechanicallyGive every role an explicit -foreground in both halves of semantic/theme.css (--success-foreground, --warning-foreground, --info-foreground, --agent-foreground today) and extend tmp/contrast-full.mjs --strict to fail any role that ships a hue without its ink. That turns "a hue primitive is never a fallback for text" from a review opinion into a gate, which is the same trick token-refs.mjs already plays.
  • Move 3 · depth as a step, focus as a rung + ringtokens/shadow.css keeps --shadow-command-palette for the one floating window, and everything else moves to tokens/radius.css 4/8/12 plus the three highlight rungs; --radius-card is the only rung that changes, so the pristine components/ui/ primitives follow with no edit. Adopt the row state pattern (fill step + 3px key-line, because highlight-low is a 1.03–1.10 luminance step and cannot carry a state alone) into ask-mode's rows and the settings list via markup, not new classes.

Cost: LOW-MEDIUM. It is a ramp plus a role model, so tokens/colors.css and semantic/theme.css carry the whole change and no component file is touched for the colour work; the -content discipline is a naming rule plus one gate line, not a rewrite. MEDIUM rather than LOW because the elevation-role rename has to land in shadow.css and radius.css together, and every existing --card/--popover consumer needs re-reading to see which named rung it actually wanted.

Biggest risk: a named-palette port is a theme, not a design system. It brings no type scale, no density contract, no focus perimeter, no status semantics and no measurement rule — it brings 15 hexes and three very good names. Adopt the elevation-role idea and the -content law; adopt the brand names into src/ and the codebase inherits an argument about whether love is the destructive colour, which is a worse version of the fight it already had about --color-purple-500. Second-order risk: the three variants in one :root invite a prefix-rebind theme switch that bypasses the .dark block, and a bypassed .dark block is precisely how the --file-* and --agent-* legibility bugs got in.
